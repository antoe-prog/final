# 결제 실패·미납·재시도·이용 정지·복구·순수납 귀속 기준 v1

- 문서 상태: 공개 가능한 운영 기준 초안
- 작성·검토일: 2026-09-19
- 적용 목적: 비자발적 이탈 감소, 기존회원 이용권 보호, 재등록·복귀 판단 정확도 향상, 실수납·순수납 과대계상 방지
- 비적용: 실제 회원·보호자 식별정보, 연락처, 카드·계좌정보, 개인별 결제 원장, 실제 가격·미납액, 승인되지 않은 추심·할인·면제 정책

## 1. 핵심 판단

1. 결제 실패는 해지 의사나 이탈 확정이 아니다.
2. 청구서 생성, 결제 시도, 승인, 매입, 정산, 실수납은 서로 다른 사건이다.
3. 재시도 예약은 실제 재시도나 성공이 아니다.
4. 결제수단 수정은 미납 해소가 아니다.
5. 미납 상태와 회원권·수업 접근 상태를 별도로 관리한다.
6. 이용 정지는 승인된 정책과 사람 검토 없이 자동 확정하지 않는다.
7. 실패 알림 발송, 전달, 열람, 사람 응답, 결제 완료를 분리한다.
8. 복구된 결제는 신규등록 매출이 아니라 기존 계약의 회수일 수 있다.
9. 환불·취소·차지백·미정산액을 제외하지 않은 금액은 순수납이 아니다.

## 5. 재시도 게이트

자동 또는 수동 재시도 전 다음을 확인한다.

1. 청구서가 유효하고 중복이 아니다.
2. 이미 실수납 또는 오프라인 납부 처리되지 않았다.
3. 환불·해지·휴회·분쟁·차지백 검토 중이 아니다.
4. 결제수단 사용 권한과 자동결제 근거가 유효하다.
5. 실패 유형이 재시도 가능한 범주다.
6. 재시도 횟수·간격·최대 기간이 승인된 정책 안이다.
7. 다음 시도 시각이 기록됐다.
8. 지점·계약·결제자 연결이 확인됐다.
9. 동일 청구에 동시 재시도가 잠겼다.
10. 실패 시 다음 상태와 사람 검토 경로가 정의됐다.

하나라도 불명확하면 자동 재시도 대신 검토 대기 상태로 보낸다.

## 6. 안내와 연락 기준

- 결제 실패 안내와 광고·재등록 판촉을 한 메시지에 섞지 않는다.
- 서비스 안내인지 광고성 정보인지 실제 목적과 최신 기준으로 별도 판단한다.
- 수신자 역할이 회원·보호자·계약자·결제자 중 누구인지 확인한다.
- 결제수단 전체 번호, 인증정보, 건강·출석정보를 메시지에 넣지 않는다.
- 안전한 공식 결제수단 수정 경로를 사용한다.
- 단축 URL·외부 결제 링크는 승인된 도메인과 일치 여부를 검증한다.
- 자동 발송 완료를 전달·열람·사람 응답으로 계산하지 않는다.
- 수신거부가 적용되는 메시지라면 채널·목적별 억제 기준을 통과한다.
- 반복 알림의 횟수·간격·중단 조건을 기록한다.
- 고객이 문제를 제기하면 재시도와 접근 변경을 보류하고 사람 검토로 전환한다.

### 자동 정지 금지 사례

- 최초 실패 1건만 존재
- 결제 처리 중 또는 지연 확인 상태
- 시스템 장애·중복 청구 의심
- 승인된 휴회·환불·해지 처리 중
- 보호자·결제자 변경 처리 중
- 오프라인 납부 확인 전
- 이의제기·분쟁 조사 중

### 정지 검토에 필요한 최소 정보

- 적용 계약·회원권
- 유효한 청구서와 납부기한
- 실패 및 재시도 이력
- 승인된 유예기간
- 고객 안내 이력
- 사람 검토자
- 적용 시각과 영향 프로그램
- 복구 조건과 정정 경로

정지는 징벌 또는 공개 표시가 아니라 계약·운영 기준에 따른 내부 접근 상태로 관리한다.

## 8. 복구 기준

1. 최신 유효 청구서의 실제 납부 또는 승인된 해결 상태를 확인한다.
2. 결제 승인만이 아니라 필요한 경우 정산 상태를 확인한다.
3. 중복 결제·초과 납부 여부를 점검한다.
4. 복구 대상 회원권·프로그램·지점을 확인한다.
5. restoration_pending에서 접근 권한 반영을 실행한다.
6. 회원 포털·예약·체크인에서 실제 접근을 확인한다.
7. restored 시각과 검증자를 기록한다.
8. 결제 복구를 재등록이나 신규등록으로 자동 계산하지 않는다.

## 9. 예외 처리

### 부분 납부

- 청구 잔액과 납부액을 분리한다.
- 부분 납부만으로 전체 청구를 완료 처리하지 않는다.
- 접근 허용 여부는 승인된 정책에 따른다.

### 오프라인 납부

- 직원의 수동 입력과 실제 수납 증빙을 구분한다.
- 수동으로 paid 표시한 사건을 자동으로 은행 정산 완료로 계산하지 않는다.

### 지연 결제수단

- 처리 중 상태에서 실패·성공을 미리 확정하지 않는다.
- 이후 반환·취소 가능성을 반영한다.

### 중복 결제

- 두 승인 중 하나를 임의 삭제하지 않는다.
- 승인·매입·정산·환불을 각각 추적한다.
- 실제 환불 완료 전 해결로 종료하지 않는다.

### 지점 이동

- 서비스 지점, 청구 지점, 수납 지점을 구분한다.
- 하나의 실수납을 여러 지점에 전액 중복 귀속하지 않는다.

## 11. 매출 계산

- 총 청구액 = 유효 청구서 금액 합계
- 결제 승인액 = 승인 성공 금액 합계
- 실수납액 = 실제 정산 확인 금액 합계
- 회수 수납액 = 결제 실패 후 같은 청구에서 정산된 금액
- 순수납액 = 실수납액 - 환불 - 차지백 - 취소·반환
- 미수 잔액 = 유효 청구액 - 적용된 실수납액 - 승인된 면제·조정액

승인, 매입, 정산 데이터를 구분할 수 없으면 실수납·순수납·ROI는 계산 불가로 표시한다.

## 12. KPI

### 결제 운영

- 결제 실패율 = 실패한 유효 시도 / 전체 유효 시도
- 재시도 실행률 = 실행된 재시도 / 재시도 적격 실패
- 회수율 = 회수된 청구 / 재시도 적격 실패 청구
- 회수 금액률 = 회수 실수납액 / 재시도 적격 미수액
- 결제수단 수정 후 성공률 = 수정 후 성공 청구 / 결제수단 수정 청구

### 고객 경험

- 잘못된 정지율 = 정정된 정지 / 전체 정지
- 복구 리드타임 = 접근 복구 확인 시각 - 해결 확인 시각
- 중복 청구율 = 확인된 중복 청구 / 전체 유효 청구
- 안내 과다율 = 승인 빈도 초과 안내 / 전체 안내

### 유지·매출

- 결제 회수 후 실제 참여율 = 회수 후 실제 참여 / 회수 완료 회원
- 결제 회수 후 재등록률 = 재등록 완료 / 회수 완료 회원
- 순수납 = 실수납 - 환불 - 차지백 - 반환

분모가 0이거나 데이터가 연결되지 않으면 계산하지 않는다.

## 13. EXP-416 — 결제 실패·재시도·정지·복구·순수납 정확도

- 기존 미수 회수의 신규등록·재등록 중복 귀속 0건

- 이 문서는 운영 구조이며 실제 미납자·금액·연락처·결제수단을 포함하지 않는다.
- Stripe와 Gymdesk 기능이 파이널유도 시스템에 연결됐다고 가정하지 않는다.
- 고객 메시지 발송, 결제 재시도, 이용 정지·복구, 환불·차지백 처리는 실행하지 않았다.
- 실제 계약·소비자 보호·전자금융·개인정보 기준은 국내 최신 법령과 전문가 검토가 필요하다.

## 17. 공개 근거

- Stripe는 결제 실패 중 재시도 가능한 경우와 새 결제수단이 필요한 경우를 구분하며, 재시도 예약·시도 횟수·다음 시도 시각과 최종 구독 상태를 별도 관리한다. <https://docs.stripe.com/billing/revenue-recovery/smart-retries>
- Stripe의 구독 상태 문서는 incomplete, past_due, unpaid, canceled, active 상태와 접근 권한·재활성 처리를 구분한다. <https://docs.stripe.com/billing/subscriptions/overview>
- Stripe는 결제 실패 알림, 결제수단 수정, 갱신 안내와 이메일 로그를 별도 기능으로 설명한다. <https://docs.stripe.com/billing/revenue-recovery/customer-emails>
- Gymdesk는 회원권 반복 결제와 회원권과 무관한 반복 청구를 분리하고, 결제 일정·방법·부분 결제·이력을 별도 관리한다. <https://docs.gymdesk.com/en/help/docs/member-payments>

외부 제품 문서는 구조 참고 자료이며 파이널유도의 실제 연결·설정·성과 근거가 아니다. 출처는 2026-09-19 확인했다.

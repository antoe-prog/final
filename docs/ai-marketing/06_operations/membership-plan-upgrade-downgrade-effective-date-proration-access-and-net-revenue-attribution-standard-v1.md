# 회원권 플랜 변경·업그레이드·다운그레이드·효력일·일할계산·이용권한·순수납 귀속 기준 v1

- 문서 상태: 공개 가능한 운영 기준 초안
- 기준일: 2026-09-19
- 적용 범위: 파이널유도멀티짐의 회원권 플랜 변경, 이용권한, 청구·정산, CRM 및 성과 측정
- 내부 회원·결제·출석 데이터: 데이터 미연결
- 주의: 이 문서는 실제 가격, 할인, 환불 또는 회원별 계약 조건을 확정하지 않는다.

## 1. 오늘의 운영 판단

회원권 변경은 하나의 사건이 아니다. 최소한 다음 사건을 분리해야 한다.

1. 회원의 변경 문의 또는 요청
2. 대상 회원권과 변경 자격 확인
3. 효력일과 예상 차액 미리보기
4. 회원의 조건 확인 및 동의
5. 변경 예약 또는 계약 반영
6. 기존 이용권한 종료와 새 이용권한 시작
7. 청구서·크레딧·일할계산 항목 생성
8. 결제 승인과 실제 정산
9. 환불·차지백·취소·재변경 반영

`변경 요청`, `변경 승인`, `플랜 적용`, `이용권한 적용`, `청구`, `실정산`을 같은 상태로 처리하지 않는다.

업그레이드는 신규등록이나 재등록이 아니며, 다운그레이드는 곧바로 해지나 이탈이 아니다. 반복매출 분석의 확장·감소와 실제 현금 수납도 구분한다.

## 2. 목적

이 기준의 목적은 다음 오분류를 막는 것이다.

- 변경 문의를 플랜 변경 완료로 계산
- 미리보기 금액을 확정 청구 또는 실제 매출로 계산
- 음수 일할계산 항목을 환불 완료로 계산
- 양수 일할계산 항목을 결제 완료로 계산
- 업그레이드를 신규회원·복귀·재등록으로 중복 계산
- 다운그레이드를 해지·이탈로 자동 분류
- 기존·신규 플랜이 동시에 유지되어 이중 청구 또는 권한 중복 발생
- 결제 변경과 이용권한 변경의 효력일 불일치 방치
- 미수납 기간에 대한 크레딧을 사람 검토 없이 확정
- 지점·채널별로 같은 플랜 변경을 여러 건의 매출로 귀속

## 4. 상태 모델

### 4.1 플랜 변경 상태

| 상태 | 의미 | 완료로 보지 않는 것 |
|---|---|---|
| `REQUESTED` | 변경 문의 또는 요청 접수 | 승인·적용 아님 |
| `ELIGIBILITY_REVIEW` | 변경 가능 여부 검토 | 견적 확정 아님 |
| `QUOTE_PREVIEWED` | 효력일·예상 차액 미리보기 생성 | 청구서·수납 아님 |
| `TERMS_ACCEPTED` | 회원이 제시된 조건 확인 | 시스템 적용 아님 |
| `CHANGE_SCHEDULED` | 미래 효력일로 변경 예약 | 현재 권한 변경 아님 |
| `CHANGE_APPLIED` | 계약의 플랜 버전 변경 완료 | 이용권한·정산 완료와 다를 수 있음 |
| `ACCESS_APPLIED` | 새 접근 권한이 실제 반영됨 | 실수납 아님 |
| `FAILED` | 변경 실행 실패 | 재시도 성공 아님 |
| `CANCELED` | 변경 요청 철회 | 환불 완료 아님 |
| `ROLLED_BACK` | 변경을 이전 상태로 복구 | 관련 청구·권한 정리 완료와 다를 수 있음 |

### 4.2 청구·정산 상태

| 상태 | 의미 |
|---|---|
| `PREVIEW_ONLY` | 변경 시 예상 차액만 계산 |
| `INVOICE_CREATED` | 실제 청구서가 생성됨 |
| `PAYMENT_PENDING` | 결제 결과를 기다리는 중 |
| `PAYMENT_AUTHORIZED` | 결제 승인, 정산 미확정 가능 |
| `PAYMENT_SETTLED` | 기준 시스템에서 실정산 확인 |
| `CREDIT_OPEN` | 계정에 크레딧이 남아 있음 |
| `CREDIT_APPLIED` | 크레딧이 실제 청구에 사용됨 |
| `REFUND_PENDING` | 환불 처리 중 |
| `REFUND_COMPLETED` | 환불 완료 확인 |
| `CHARGEBACK` | 분쟁·차지백 발생 |
| `VOIDED` | 청구 취소 또는 무효화 |

음수 일할계산은 `REFUND_COMPLETED`가 아니고, 양수 일할계산은 `PAYMENT_SETTLED`가 아니다.

## 5. 효력일 기준

플랜 변경에는 다음 날짜를 각각 기록한다.

- 요청일
- 견적 생성일과 견적 만료일
- 조건 확인일
- 계약 변경 예정일
- 계약 변경 실제 적용일
- 기존 이용권한 종료일
- 신규 이용권한 시작일
- 청구서 생성일
- 결제 승인일
- 실정산일
- 환불 완료일

지원 가능한 효력일 유형은 승인된 운영 정책에 따라 다음 중 하나로 제한한다.

- 즉시 변경
- 다음 갱신일 변경
- 특정 승인일 변경

어떤 유형이든 고객 안내 문구, 계약, 이용권한, 청구서에 동일한 기준일을 연결한다. 한 화면에 변경 완료가 표시되더라도 다른 시스템의 권한·청구 반영을 별도로 검증한다.

## 6. 플랜 교체와 중복 방지

새 플랜을 추가하면서 기존 플랜을 종료하지 않으면 두 가격 또는 두 이용권한이 동시에 유지될 수 있다. 따라서 변경 실행에는 다음 검사가 필요하다.

1. 변경 대상 기존 회원권 항목을 명시적으로 지정
2. 기존 플랜의 종료 또는 대체 상태 확인
3. 새 플랜의 시작일과 버전 확인
4. 겹치는 청구 항목 탐지
5. 겹치거나 비는 이용권한 기간 탐지
6. 실패 시 계약·청구·권한을 함께 복구할 수 있는 이력 보존

복수 회원권을 합법적으로 보유하는 경우는 예외 규칙과 승인 근거를 별도로 기록한다.

## 7. 이용권한 기준

결제 설정과 실제 수업 접근은 별도 검증한다.

- 접근 가능한 지점
- 접근 가능한 프로그램과 회차
- 주·월·전체 이용 횟수
- 예약 가능 시점과 정원 규칙
- 남은 회차의 이월 가능 여부
- 이월 상한과 만료일
- 일시정지·휴회·복구 상태
- 가족·보호자 결제와 실제 참여자별 권한

변경 후 권한 차이가 있을 때는 다음을 자동으로 가정하지 않는다.

- 남은 회차가 새 플랜으로 모두 이동
- 기존 혜택과 할인이 유지
- 모든 지점에서 즉시 사용 가능
- 예약된 수업이 자동 유지 또는 취소
- 휴회·연장 기간이 자동 재계산

## 8. 일할계산·크레딧 기준

일할계산은 미리보기와 실제 청구를 분리한다.

### 8.1 미리보기 필수 항목

- 기존 플랜과 신규 플랜 버전
- 계산 기준 시각과 시간대
- 효력일
- 남은 기간
- 차액의 방향: 추가 청구 또는 크레딧
- 할인·세금 적용 여부
- 통화와 반올림 규칙
- 견적 만료일
- 실제 청구와 차이가 날 수 있는 조건

### 8.2 금지되는 등식

- 음수 일할계산 = 현금 환불
- 양수 일할계산 = 실수납
- 청구서 생성 = 결제 성공
- 결제 승인 = 정산 완료
- 크레딧 생성 = 다음 청구 적용
- 변경 예약 = 현재 이용권한 변경

### 8.3 미수납 청구가 있는 경우

기존 청구서가 아직 미수납인데 남은 기간 크레딧을 자동 확정하면 실제로 지급되지 않은 기간에 대한 크레딧이 생길 수 있다. 다음 중 하나라도 해당하면 사람 검토 대상으로 보낸다.

- 이전 청구서가 미납·실패·분쟁 상태
- 부분결제 또는 현장결제가 섞임
- 할인·쿠폰·가족 결제가 연결됨
- 여러 참여자의 권한이 한 결제에 묶임
- 이미 환불 또는 차지백이 진행 중

## 9. 업그레이드·다운그레이드 분류

### 9.1 업그레이드

업그레이드는 가격, 기간, 프로그램 접근, 회차 또는 지점 범위가 확대되는 변경 후보이다. 그러나 다음을 모두 확인하기 전에는 성과로 확정하지 않는다.

- 새 플랜이 실제 적용됨
- 새 이용권한이 실제 반영됨
- 관련 청구가 생성됨
- 실제 결제 정산이 확인됨
- 환불·차지백·취소가 반영됨

업그레이드는 반복매출 분석에서 `확장` 후보가 될 수 있지만 신규회원·복귀·재등록으로 중복 계산하지 않는다.

### 9.2 다운그레이드

다운그레이드는 가격, 기간, 프로그램 접근, 회차 또는 지점 범위가 축소되는 변경 후보이다. 회원권이 계속 유효하면 해지 또는 이탈로 계산하지 않는다.

반복매출 분석에서는 `감소` 후보가 될 수 있으나, 실제 순수납 감소는 정산·크레딧·환불을 확인한 후 별도 계산한다.

### 9.3 중립 변경

동일 가치의 플랜 교체, 지점 이동, 결제주기 변경, 오류 정정은 신규·복귀·재등록·확장·감소 어느 하나로 자동 분류하지 않는다. 승인된 분류 규칙을 적용한다.

## 10. 매출 귀속 기준

### 10.1 반복매출 지표

공식 정의가 승인된 경우에만 다음 구조를 사용한다.

`기간말 반복매출 = 기간초 반복매출 + 신규 + 복귀 + 확장 - 감소 - 이탈 ± 기타 조정`

이 식의 `확장`과 `감소`는 계약상 반복매출 변화이며, 실제 현금 수납과 동일하지 않다.

### 10.2 순수납

`순수납 = 실정산 금액 - 실제 환불 - 차지백 - 취소 정산`

내부 결제 원장이 연결되지 않았으므로 현재 순수납은 데이터 미연결·계산 불가다.

### 10.3 귀속 금지

- 업그레이드를 신규등록과 재등록에 동시 귀속
- 다운그레이드를 이탈과 감소에 동시 귀속
- 같은 변경을 접점·지점별로 전액 중복 귀속
- 크레딧·환불을 차감하지 않은 매출 보고
- 예상 차액을 실제 수납으로 보고
- 가족 결제 한 건을 참여자별 전액 매출로 복제

## 11. 채널별 실행 가드레일

### 네이버·Google·홈페이지

- 승인된 플랜명·효력일·가격 버전만 공개
- 일반 안내와 개인별 예상 차액을 분리
- 변경 가능 여부를 확정 전 약속하지 않음
- 구버전 노출을 채널별로 확인

### 당근

- 동네 홍보 문구에서 `즉시 업그레이드`, `자동 환불`, `차액 없음`을 근거 없이 사용하지 않음
- 특정 지점·프로그램의 실제 적용 가능 여부를 확인

### Instagram

- 코치 개인 계정 @ant.toe.98을 공식 결제·계약 발표 주체로 표현하지 않음
- 승인되지 않은 가격·할인·무료·환불·갱신 약속을 포함하지 않음
- 교육 콘텐츠의 행동 유도는 하나만 사용
- 개별 승인 대기 미디어·캡션은 승인 전 외부 업로드·예약·공개 저장소 게시 금지

## 12. CRM 후속 기준

회원에게 실제 안내하기 전 다음 필드를 갖춘다.

- 대상 회원권과 플랜 버전
- 요청 유형과 요청 시각
- 변경 자격 확인 결과
- 효력일 유형
- 예상 차액과 견적 유효기간
- 기존·신규 이용권한 차이
- 취소·재변경·환불 기준
- 안내 채널과 광고성 정보 수신 동의 범위
- 담당자와 승인자

서비스 이행 안내와 광고성 업셀 권유는 목적·동의·발송 기록을 분리한다. 실제 메시지 발송은 대표 승인과 운영 권한이 확인된 후에만 수행한다.

## 13. 역할별 체크리스트

### CMO

- 신규 유입 확대 전에 플랜·권한·정산 정의를 승인
- 확장매출과 신규등록 매출의 중복 방지
- 단기 매출보다 회원 이해 가능성과 신뢰를 우선

### Growth Analyst

- 요청·견적·동의·적용·권한·청구·정산을 분리
- 업그레이드·다운그레이드·중립 변경을 별도 집계
- 미성숙·미수납·환불 진행 건을 성과에서 제외

### Acquisition Marketer

- 플랜 변경 혜택을 신규 체험 혜택처럼 표현하지 않음
- 승인된 가격·조건이 없으면 문의 CTA만 사용

### CRM Marketer

- 만료예정·휴면·기존회원의 변경 제안을 별도 세그먼트로 운영
- 자동응답을 사람의 설명·동의로 계산하지 않음
- 서비스 알림과 광고성 권유를 분리

### Content Strategist

- 플랜명·금액보다 이용 방식과 확인 질문을 설명
- 개인 코치 계정에서 공식 계약 확약을 하지 않음
- 하나의 게시물에는 하나의 행동 유도만 사용

### Experiment Manager

- 실데이터 연결 전 합성 데이터로 상태 전이와 중복 귀속을 검증
- 오류가 하나라도 나오면 자동 변경·자동 안내·성과 보고를 중단

### Auditor

- 개인정보·결제수단·개인별 원장을 공개하지 않음
- 미확정 가격·환불·혜택을 공개 자료로 만들지 않음
- 승인 대기 Instagram 미디어·캡션을 공개 저장소에서 제외

## 15. 승인 게이트

- 공식 플랜과 버전 식별자
- 업그레이드·다운그레이드·중립 변경 정의
- 변경 자격과 제외 조건
- 즉시·다음 갱신·특정일 효력 규칙
- 일할계산·할인·세금·반올림 기준
- 미납·부분결제·환불·차지백 처리
- 프로그램·회차·지점별 이용권한
- 남은 회차·이월·휴회·예약 처리
- 가족·보호자·참여자별 권한과 매출 배분
- 안내 문구·채널·담당자·승인자
- 확장·감소·순수납 귀속 기준

## 16. 실험 EXP-419

### 가설

상태·효력일·권한·일할계산·정산을 분리하면 플랜 변경을 신규등록·재등록·이탈·실매출로 잘못 계산하지 않는다.

### 합성 데이터 범위

- 회원권 480건
- 플랜 변경 요청 960건
- 이용권한 사건 1,920건
- 청구서·일할계산 항목 2,880건
- 결제·환불·차지백 사건 2,400건

실제 회원·연락처·출석·결제 데이터는 사용하지 않는다.

### 성공 기준

- 변경 요청의 적용 완료 오분류 0건
- 견적 미리보기의 실제 청구 오분류 0건
- 음수 일할계산의 환불 완료 오분류 0건
- 양수 일할계산의 실정산 오분류 0건
- 미수납 기간에 대한 자동 크레딧 확정 0건
- 기존·신규 플랜의 비승인 동시 활성·이중 청구 0건
- 미검토 이용권한 공백·중복 0건
- 업그레이드의 신규·복귀·재등록 중복 귀속 0건
- 다운그레이드의 해지·이탈 오분류 0건
- 지점·채널별 전액 중복 귀속 0건
- 환불·차지백 미차감 0건
- 승인 없는 고객 안내·계정 변경·Instagram 업로드 0건

### 중단 기준

위 항목 중 하나라도 실패하면 실제 자동 플랜 변경, 권한 변경, 고객 안내, 매출·유지 성과 보고를 중단하고 사람 검토로 전환한다.

## 18. 공개 채널 적용 메모

현재 확인 가능한 Instagram 승인 대기본은 실제 가격·할인·무료·환불·플랜 변경 약속을 포함하지 않는 상태를 유지한다. 새 콘텐츠는 기존 승인 대기 작업이 처리되기 전 추가 제작하지 않는다.

회원권 변경 안내를 공개 콘텐츠로 만들 경우 실제 플랜·효력일·가격·환불 기준이 승인된 뒤 별도 검수한다. 코치 개인 계정은 결제·계약의 공식 발표 계정으로 사용하지 않는다.

## 19. 근거 출처와 적용 한계

1. [Stripe — Prorations](https://docs.stripe.com/billing/subscriptions/prorations) — 2026-09-19 확인. 업그레이드·다운그레이드 시 일할계산, 음수 크레딧과 양수 청구의 처리, 미수납 청구가 있을 때의 위험을 확인했다. Stripe의 기능을 파이널유도가 사용 중이라고 가정하지 않았다.
2. [Stripe — Change the price of existing subscriptions](https://docs.stripe.com/billing/subscriptions/change-price) — 2026-09-19 확인. 기존 구독 항목을 명시적으로 교체하지 않으면 기존·신규 가격이 함께 남을 수 있고, 결제주기 변경은 청구 기준일에 영향을 줄 수 있음을 확인했다.
3. [Stripe — Billing analytics](https://docs.stripe.com/billing/subscriptions/analytics) — 2026-09-19 확인. 반복매출의 신규·복귀·확장·감소·이탈 구분을 참고했다. 추정·반복매출 지표를 실제 순수납으로 사용하지 않았다.
4. [Gymdesk — Setting Up Memberships](https://docs.gymdesk.com/en/help/docs/membership-options) — 2026-09-19 확인. 회원권의 가격 방식, 결제 시작, 기간·갱신, 프로그램·회차 접근과 이월 조건이 별도 설정임을 확인했다. 해당 시스템이 파이널유도에 연결됐다고 가정하지 않았다.
5. [Gymdesk — Member Payments](https://docs.gymdesk.com/en/help/docs/member-payments) — 2026-09-19 확인. 회원권 반복결제와 별도 반복결제, 일정 결제와 결제 이력의 구분을 확인했다.

## 20. 감사 결과

- 실제 회원수·전환율·유지율·매출은 추정하지 않았다.
- 실제 가격·할인·환불·플랜·지점 조건을 만들지 않았다.
- 회원·보호자 식별정보, 연락처, 출석·건강·결제 원장을 포함하지 않았다.
- 미확정 행사와 내부 예산·손익·목표 인원을 포함하지 않았다.
- 승인 대기 Instagram 이미지와 캡션을 공개 문서에 포함하지 않았다.
- 외부 고객 메시지, 광고, 플랜 변경, 결제, 계정 변경 또는 게시를 실행하지 않았다.

# 회원권 결제 실패·회수·순정산 판정 기준 v1

- 문서 상태: 공개 운영 기준 초안
- 작성일: 2026-09-15 (Asia/Seoul)
- 적용 범위: 정기 회원권과 승인된 분할·반복 결제의 실패, 재시도, 회원 안내, 회수, 환불·분쟁, 순수납 집계
- 현재 상태: 결제사·계약·회원권·출석·회계 데이터 미연결
- 외부 행동: 결제 재시도, 고객 메시지, 이용 제한, 할인·혜택, 계정 설정 변경 미실행

## 1. 목적

결제 실패 한 건을 곧바로 해지, 이탈, 미수금 확정 또는 매출 손실로 처리하지 않는다.

이 기준은 다음 사건을 분리한다.

`결제 예정 → 결제 시도 → 처리 중 → 승인 실패 → 재시도 적격 검토 → 재시도 → 승인 성공 → 정산 확인 → 환불·분쟁 반영 → 순수납 확정`

목표는 다음 네 가지다.

1. 일시적 승인 실패로 회원 관계가 불필요하게 끊어지는 것을 방지한다.
2. 결제 재시도와 고객 안내가 계약·결제사 정책·승인된 운영 규칙을 따르게 한다.
3. 승인 성공, 실제 정산, 환불, 차지백을 서로 다른 증거로 관리한다.
4. 회수 건수보다 회원 선택권, 기록 완전성, 검증 순수납을 우선한다.

## 2. 핵심 원칙

### 2.1 결제 실패는 해지가 아니다

- 승인 실패만으로 회원이 해지를 원한다고 추정하지 않는다.
- 결제 실패만으로 회원권 해지 완료, 휴면, 재등록 필요 상태로 바꾸지 않는다.
- 실제 계약 효력은 계약 원천과 승인된 정책에서 별도로 확인한다.
- 회원이 명시적으로 해지를 요청하면 결제 회수 경로와 해지 처리 경로를 분리한다.

### 2.2 재시도 예약은 실행이 아니다

- 재시도 적격 판정, 재시도 예약, 실제 재시도, 승인 결과를 각각 기록한다.
- 재시도 카운터 증가가 실제 결제 시도 또는 청구 발생을 뜻하지 않을 수 있다.
- 결제사가 재시도하지 않는 오류와 새 결제수단이 필요한 오류를 구분한다.
- 결제사별 오류 코드와 재시도 규칙은 해당 결제사의 최신 공식 문서를 기준으로 한다.

### 2.3 승인 성공은 순수납 확정이 아니다

- 승인 성공 또는 결제 완료와 지급·정산 완료를 분리한다.
- 환불, 부분 환불, 취소, 차지백, 수수료, 상계 상태를 별도 사건으로 기록한다.
- 마케팅 성과에는 승인액이 아니라 정의된 기준 원천의 검증 순수납액만 사용한다.
- 순수납은 회계상 매출총이익이나 순이익과 동일하지 않다.

### 2.4 회원 안내와 광고를 분리한다

- 특정 결제 실패와 해결 방법을 알리는 운영 안내를 할인·행사·추가 구매 권유와 섞지 않는다.
- 다른 상품, 장기권, 추천 혜택을 함께 제안하려면 별도 승인과 광고성 정보 기준을 검토한다.
- 연락 중단 또는 채널 변경 요청이 확인되면 승인된 절차에 따라 반영한다.
- 결제정보 전체, 카드번호, 인증값, 비밀키를 상담 메모나 공개 문서에 복사하지 않는다.

## 3. 표준 상태

한 결제 사건은 현재 상태와 근거를 가진다. 이전 상태는 덮어쓰지 않고 이력으로 남긴다.

| 코드 | 의미 | 최소 증거 | 금지되는 해석 |
|---|---|---|---|
| `PAYMENT_DUE` | 계약상 결제 예정 | 계약·청구 원천의 예정일 | 실제 청구·미납 |
| `PAYMENT_ATTEMPT_CREATED` | 결제 시도 객체 생성 | 결제사 사건 ID·시각 | 승인 성공 |
| `PAYMENT_PROCESSING` | 비동기 처리 중 | 결제사 상태·조회 시각 | 실패·수납 완료 |
| `PAYMENT_ACTION_REQUIRED` | 인증·결제수단 갱신 등 회원 조치 필요 | 공식 상태·오류 분류 | 해지 의사 |
| `PAYMENT_FAILED_VERIFIED` | 결제사 원천에서 승인 실패 확인 | 사건 ID·실패 시각·표준 오류군 | 미수 확정·회원 이탈 |
| `RETRY_ELIGIBILITY_REVIEW` | 재시도 가능 여부 검토 | 오류군·계약·정책 버전 | 재시도 승인 |
| `RETRY_SCHEDULED` | 승인된 규칙에 따라 재시도 예정 | 예정 시각·규칙 버전 | 실제 재시도 |
| `RETRY_EXECUTED` | 결제사가 실제 재시도 | 새 시도 ID·시각 | 성공 |
| `PAYMENT_METHOD_UPDATE_REQUESTED` | 안전한 갱신 경로 안내 | 안내 채널·시각·승인 문구 버전 | 정보 갱신 완료 |
| `PAYMENT_METHOD_UPDATED_VERIFIED` | 기준 시스템에서 갱신 확인 | 결제사 원천·확인 시각 | 회수 성공 |
| `PAYMENT_SUCCEEDED_VERIFIED` | 결제사에서 성공 확인 | 성공 사건 ID·금액·시각 | 정산·순수납 확정 |
| `SETTLEMENT_PENDING` | 지급·정산 대기 | 지급 예정 또는 잔액 상태 | 회계 수납 완료 |
| `SETTLEMENT_VERIFIED` | 기준 원천에서 정산 확인 | 정산 ID·일자·금액 | 환불·분쟁 없음 |
| `REFUND_PENDING` | 환불 승인 또는 처리 중 | 환불 사건 ID·상태 | 환불 완료 |
| `REFUND_SETTLED_VERIFIED` | 환불 완료 확인 | 환불 완료 시각·금액 | 분쟁 종료 |
| `DISPUTE_OPEN` | 결제 분쟁·차지백 진행 중 | 분쟁 사건 ID·개시일 | 최종 손실 |
| `DISPUTE_CLOSED_VERIFIED` | 분쟁 결과 확인 | 결과·금액·종료일 | 자동 재등록·해지 |
| `RECOVERY_STOPPED` | 추가 회수 절차 중단 | 중단 사유·권한·시각 | 계약 해지 완료 |
| `DATA_REVIEW_REQUIRED` | 원천 충돌·누락 | 충돌 필드·담당·기한 | 임의 성공·실패 |

## 4. 상태 전이

### 4.1 정상 경로

`PAYMENT_DUE → PAYMENT_ATTEMPT_CREATED → PAYMENT_PROCESSING 또는 PAYMENT_SUCCEEDED_VERIFIED → SETTLEMENT_PENDING → SETTLEMENT_VERIFIED`

처리 중 상태는 성공이나 실패로 미리 계산하지 않는다.

### 4.2 회수 경로

`PAYMENT_FAILED_VERIFIED → RETRY_ELIGIBILITY_REVIEW → RETRY_SCHEDULED → RETRY_EXECUTED`

재시도 결과는 다음 중 하나로 연결한다.

- `PAYMENT_SUCCEEDED_VERIFIED`
- `PAYMENT_FAILED_VERIFIED`
- `PAYMENT_ACTION_REQUIRED`
- `DATA_REVIEW_REQUIRED`

### 4.3 결제수단 갱신 경로

`PAYMENT_ACTION_REQUIRED → PAYMENT_METHOD_UPDATE_REQUESTED → PAYMENT_METHOD_UPDATED_VERIFIED → RETRY_ELIGIBILITY_REVIEW`

갱신 확인만으로 회수 성공으로 계산하지 않는다.

### 4.4 환불·분쟁 경로

`PAYMENT_SUCCEEDED_VERIFIED 또는 SETTLEMENT_VERIFIED → REFUND_PENDING → REFUND_SETTLED_VERIFIED`

`PAYMENT_SUCCEEDED_VERIFIED 또는 SETTLEMENT_VERIFIED → DISPUTE_OPEN → DISPUTE_CLOSED_VERIFIED`

성공 결제의 원래 상태가 남아 있더라도 후속 환불·분쟁을 순수납에 반영한다.

## 5. 오류 분류

결제사 원문 코드는 비공개 원천에 보존하고 공개 집계에는 아래 표준군만 사용한다.

| 오류군 | 설명 | 기본 조치 |
|---|---|---|
| `TEMPORARY_RETRYABLE` | 일시적 실패 가능성이 있는 상태 | 결제사·내부 정책의 재시도 적격 검토 |
| `CUSTOMER_ACTION_REQUIRED` | 인증 또는 안전한 결제수단 갱신 필요 | 승인된 운영 안내 검토 |
| `NON_RETRYABLE` | 자동 재시도가 적절하지 않은 상태 | 반복 재시도 중단, 안전한 다음 단계 검토 |
| `PROCESSING_UNKNOWN` | 비동기 처리 또는 최종 상태 미확인 | 확정 전 대기·재조회 |
| `DUPLICATE_OR_TEST` | 중복 이벤트 또는 테스트 사건 | 실제 KPI에서 제외, 감사 로그 보존 |
| `SOURCE_CONFLICT` | 결제사·회원권·회계 원천 충돌 | `DATA_REVIEW_REQUIRED` |
| `UNCLASSIFIED` | 분류 근거 부족 | 임의 재시도 금지, 담당 검토 |

오류군 자체로 회원의 경제 상황, 고의 미납, 불만, 이탈 의도를 추정하지 않는다.

## 6. 재시도 적격성

재시도 실행 전 다음을 확인한다.

1. 적용되는 계약과 결제 동의가 유효하다.
2. 결제사 원천에서 실패 사건과 오류군이 확인된다.
3. 같은 청구의 중복 성공 또는 처리 중 사건이 없다.
4. 결제사와 내부 정책상 재시도가 허용된다.
5. 회원의 해지·결제 중단·분쟁 요청과 충돌하지 않는다.
6. 재시도 횟수·기간·종료 기준이 대표 승인된 정책 안에 있다.
7. 결제수단 갱신이 필요한 경우 안전한 공식 경로만 사용한다.

다음 경우 자동 재시도를 보류한다.

- 최종 결제 상태가 아직 `PROCESSING`이다.
- 같은 청구에 성공 사건이 존재한다.
- 환불 또는 분쟁이 진행 중이다.
- 계약 효력이나 청구 금액이 원천마다 다르다.
- 회원이 해지 또는 결제 중단을 명시했고 처리 중이다.
- 오류 코드가 재시도 불가이거나 분류되지 않았다.
- 결제사·시스템의 최신 정책을 확인할 수 없다.

## 7. 회원 연락 통제

### 7.1 운영 안내 최소 내용

- 어떤 계약·청구에 관한 안내인지 식별 가능한 최소 정보
- 결제가 완료되지 않았다는 확인된 상태
- 회원이 취할 수 있는 안전한 다음 단계
- 문의 가능한 공식 채널
- 재시도 여부와 시점은 승인·검증된 경우에만 표시

### 7.2 금지 내용

- 카드번호, 계좌번호, 인증번호, 비밀번호 회신 요청
- 확인되지 않은 연체료·위약금·이용 제한 통보
- 실패 사유를 회원의 책임으로 단정
- 결제 해결 안내에 미승인 할인·상품 판매를 결합
- 같은 오류에 대한 무제한 반복 연락
- 개인 결제 상태를 공개 댓글이나 공개 채널에서 논의

### 7.3 채널 전환

- 회원이 문의한 채널에서 안전하게 해결할 수 없으면 공식 보안 경로를 안내한다.
- 다른 채널로 전환할 때는 목적·동의·연락 가능 상태를 확인한다.
- Instagram DM은 결제 원장이나 카드 정보 수집 채널로 사용하지 않는다.
- 코치 개인 계정 `@ant.toe.98`에서 회원 결제 문제를 접수·해결했다고 주장하지 않는다.

## 8. 회원권·출석 처리 경계

- 결제 실패 직후 이용 가능 여부는 계약·회원권 정책으로 결정하며 이 문서가 자동 정지 기준을 만들지 않는다.
- 이용 제한 전 실제 결제 상태, 계약 효력, 예외 승인, 안내 이력을 확인한다.
- 결제 회수 성공은 출석, 만족, 재등록을 뜻하지 않는다.
- 출석 지속은 결제 완료나 매출 확정을 뜻하지 않는다.
- 지점 이동 또는 교차 출석은 원래 결제 사건과 별도 운영 사건으로 관리한다.

## 9. 순수납 정의

### 9.1 검증 회수액

`결제 실패 뒤 동일 청구 또는 승인된 대체 청구에서 SETTLEMENT_VERIFIED 된 금액`

재시도 예약, 결제수단 갱신, 승인 성공만으로는 회수액에 포함하지 않는다.

### 9.2 검증 순수납액

`정산 확인 금액 - 완료 환불액 - 확정 차지백액 - 확인된 상계액`

결제 수수료와 기타 비용이 연결되지 않으면 기여이익 또는 ROI를 계산하지 않는다.

### 9.3 회수 순증분

자동 또는 수동 회수 활동의 증분 효과는 적절한 대조군이나 사전 승인된 비교 설계가 있을 때만 계산한다.

자연 회복, 카드 자동 갱신, 회원의 자발적 재결제를 특정 메시지 성과로 임의 귀속하지 않는다.

## 10. 필수 데이터 필드

실제 식별정보와 결제 원장은 비공개 시스템에만 저장한다.

| 영역 | 필수 필드 |
|---|---|
| 사건 | 비식별 결제 사건 키, 청구 키, 지점 코드, 발생 시각 |
| 계약 | 계약 키 해시, 계약 상태, 약관·정책 버전 |
| 결제 | 결제사, 상태, 오류군, 시도 번호, 결제사 사건 ID |
| 재시도 | 적격 판정, 규칙 버전, 예정·실행 시각, 결과 |
| 연락 | 목적, 채널, 문구 버전, 시도·도달·응답 시각, 중단 상태 |
| 회원권 | 효력 상태, 이용 제한 여부, 근거 정책, 예외 승인 |
| 정산 | 승인액, 정산액, 정산일, 기준 원천 |
| 차감 | 환불·취소·차지백·상계 금액과 완료 상태 |
| 결과 | 회수 상태, 계약 지속, 실제 출석, 관찰 종료일 |
| 감사 | 담당 역할, 검증 시각, 원천 충돌, 예외 사유 |

## 11. KPI 정의

분자·분모·기간·기준 원천이 모두 있을 때만 계산한다.

### 11.1 결제 실패 분류 완전율

`오류군·계약·중복 여부가 확인된 실패 사건 수 ÷ 전체 검증 실패 사건 수`

### 11.2 재시도 실행 정확률

`적격 판정과 정책 버전이 기록된 실제 재시도 수 ÷ 전체 실제 재시도 수`

### 11.3 회수율

`관찰기간 내 SETTLEMENT_VERIFIED 된 실패 청구 수 ÷ 관찰기간이 종료된 검증 실패 청구 수`

미성숙 사건은 분모에서 제외한다.

### 11.4 결제 안내 해결률

`안내 뒤 PAYMENT_SUCCEEDED_VERIFIED 또는 승인된 종료 상태에 도달한 사건 수 ÷ 도달 확인된 결제 안내 사건 수`

자연 회복과 메시지 기여를 구분하지 못하면 단순 관찰 지표로만 사용한다.

### 11.5 중복 청구 사고율

`중복 성공 또는 승인 없는 중복 청구 사건 수 ÷ 전체 실제 결제 시도 수`

분모가 0이면 계산하지 않는다.

### 11.6 검증 순수납액

정의된 정산·환불·차지백 원천을 연결한 뒤 계산한다. 현재 상태는 `데이터 미연결`이다.

## 13. 역할별 운영

### CMO

- 신규 광고 확대 전에 결제 실패로 인한 비자발적 이탈과 순수납 누락을 별도 병목으로 본다.
- 회수율만 높이는 방식이 회원 경험·분쟁·브랜드 위험을 키우지 않는지 검토한다.

### Growth Analyst

- 실패, 재시도, 성공, 정산, 환불, 분쟁의 각 사건을 연결한다.
- 자연 회복과 캠페인 기여를 분리한다.

### Acquisition Marketer

- 할인·무료 체험으로 결제 실패를 덮지 않는다.
- 신규 등록 결제에서도 처리 중·실패·성공·정산을 구분한다.

### CRM Marketer

- 운영 안내와 광고성 후속을 분리한다.
- 문구·채널·횟수·종료 기준 승인 전 실제 메시지를 발송하지 않는다.

### Content Strategist

- 공개 콘텐츠에 결제 실패 사례, 개인 금액, 미확정 정책을 사용하지 않는다.
- 검증된 일반 결제·문의 안내가 필요하면 공식 채널에서만 공개한다.

### Experiment Manager

- 실험 전 기준선과 관찰기간을 확정한다.
- 회수 성공 외에 중복 청구, 분쟁, 연락 거부, 오류를 함께 본다.

### Auditor

- 결제 승인과 정산, 환불, 차지백을 대조한다.
- 개인정보·결제수단 정보·비밀키가 공개 문서와 로그에 없는지 확인한다.

## 14. EXP-319 — 결제 실패 회수 판정 완전성

- 대상: 대표 승인·데이터 연결 뒤 최초 검증 실패 청구 20건 또는 30일
- 목적: 회수율 개선 전 상태 판정과 통제의 완전성 검증
- 성공 기준:
  - 실패 사건의 오류군·계약·중복 검증률 100%
  - 실제 재시도의 적격 판정·정책 버전 기록률 100%
  - 승인 성공·정산·환불·차지백 혼합 0건
  - 처리 중 결제의 조기 실패·성공 판정 0건
  - 승인 없는 반복 재시도·고객 연락·이용 제한 0건
  - 중복 청구 0건
  - 공개 저장소 개인정보·결제정보 0건
- 보류 기준:
  - 결제사·계약·회원권·회계 원천 미연결
  - 재시도 횟수·기간·연락·이용 제한 정책 미승인
  - 관찰기간 미성숙
- 중단 기준:
  - 해지 요청 뒤 승인 없는 재청구
  - 결제수단 정보를 DM·문자 회신으로 요구
  - 미확인 승인액을 매출 또는 회수 성과로 보고
  - 분쟁·환불 진행 중 반복 청구
- 현재 기준선: 데이터 미연결

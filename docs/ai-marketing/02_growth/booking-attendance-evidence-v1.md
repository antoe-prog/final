# 예약상태·실제 출석·동기화 복구 — 계측 규격 v1

- 최초 작성 기준일: 2026-09-10
- 최신 업데이트: 2026-09-12
- 상태: 설계 완료 / 운영DB 적용 없음 / 실제 데이터 검증 전
- 내부 예약·출석·결제·전환 데이터: **데이터 미연결**
- 공개 범위: 회원·보호자 식별정보, 연락처, 예약자명, 개인별 출석·건강·결제 원장, 비밀키·토큰은 포함하지 않는다.

## 1. 정정할 전제

네이버의 예약 이용완료 상태만으로 실제 방문을 확정하지 않는다. 공식 안내에는 이용종료 이후 자동 이용완료 처리가 설명되어 있고 유형·설정별 예외도 있다. 파이널유도의 상품 유형·설정은 미확인이다. [S1]

따라서 이전 대화의 `네이버 이용완료 = 실제 체험 방문`으로 읽힐 수 있는 집계 설계는 사용하지 않는다. 이는 특정 회원의 노쇼나 집계 오류가 실제 발생했다는 주장이 아니라 측정 규칙의 정정이다.

## 2. 2026-09-12 신규 변화 — 예약은 들어오는데 관리·연동은 잠시 멈출 수 있다

네이버 스마트플레이스는 2026-09-09 예약 서비스 시스템 점검 공지를 게시했고, 2026-09-10 02:00~05:00 동안 다음 동작 차이를 공식적으로 안내했다. [S3]

- 이용자의 예약 신청은 점검 중에도 정상 접수될 수 있다.
- 사업자의 예약 관리 메뉴는 점검 중 이용이 제한될 수 있다.
- 연동 파트너사의 스케줄·재고·요금·휴무일 관련 API 호출은 실패 응답을 받을 수 있다.
- 점검 중 실패한 연동 요청은 점검 종료 후 다시 요청해야 한다.
- 점검 중 접수된 예약은 점검 종료 후 관리 메뉴에서 확인할 수 있다.

이 차이는 파이널유도에 중요한 운영 리스크를 만든다.

`고객이 예약을 넣었다`와 `도장 운영시스템이 그 예약을 즉시 확인·동기화했다`는 같은 사건이 아니다.

따라서 신규 체험 퍼널에서 아래 상태를 분리해야 한다.

`booking_received` → 외부 플랫폼에서 예약 접수 사실 존재

`booking_synced` → 내부 운영시스템 또는 담당자 관리화면에서 예약 확인

`booking_reconciled` → 장애·점검 후 누락·중복·변경사항을 대조 완료

`verified_attendance` → 현장에서 실제 방문 확인

이 규격은 네이버가 항상 장애가 난다는 가정이 아니다. 공식적으로 `예약 접수는 계속되지만 관리/API는 제한될 수 있는 시간대`가 존재한다는 사실을 반영하는 복구 설계다.

## 4. 방문률의 단위와 분모

초기 설계에서는 `참가자 한 명의 확정 예약 회차`를 하나의 단위로 삼는다. 예약자 한 명이 가족 여러 명을 예약했다면 예약 건수와 참가자 수를 섞지 않는다.

관찰기간에 예정 수업이 종료된 확정 예약 참가자-회차 집합을 N으로 둔다. 사업자 취소와 일정 변경 전의 이관 회차는 제외하되 제외 건수를 별도로 기록한다. 변경 후 예약은 새 예정일이 관찰조건을 충족할 때 포함한다.

집합 N은 다음 네 상태로 빠짐없이 분류한다.

- V: 현장 방문 확인
- C: 고객 취소 확인
- Z: 수업 종료 후 담당자가 불참을 확인한 노쇼
- U: 출석 여부 미확인

검증식: **N = V + C + Z + U**

N이 0이거나 U가 1 이상이면 방문률·노쇼율 점추정은 보류한다. 누락을 0으로 대체하지 않는다. 이미 알려진 V, C, Z, U의 수와 데이터 완결성을 먼저 보고한다.

U가 0이고 N이 0보다 크면:

- 확정예약 기준 실방문율 = V ÷ N × 100
- 고객취소율 = C ÷ N × 100
- 확정예약 기준 노쇼율 = Z ÷ N × 100

이 규격의 방문률은 고객 취소를 포함하는 분모를 사용한다. 다른 대시보드의 `취소 제외 방문률`과 직접 비교하지 않는다.

## 5. 등록·매출은 또 다른 단위

첫 체험 후 등록률은 동일한 신규 체험자 집단을 기준으로 중복을 제거해 계산한다. 다회 체험자의 방문 회차를 사람 수로 세지 않는다.

제안 관찰기간은 첫 체험 후 14일이다. 이는 성과나 업계 기준이 아니라 이번 파일럿의 설계값이며 시행 전에 고정한다. 14일이 지나지 않은 체험자는 아직 결과가 확정되지 않은 집단으로 분리한다.

- D: 신규 첫 체험이 현장에서 확인되고 정해진 관찰기간이 지난 고유 인원
- R: D 중 관찰기간 안에 첫 유료등록이 확인된 인원
- 체험→유료등록률 = R ÷ D × 100

내부 등록확인 누락이 있거나 D가 0이면 계산하지 않는다. 기존회원·복귀회원은 별도 집단이다. 결제 이후 취소·환불은 별도 기재한다. 수납액에서 환불액을 차감한 값은 해당 기간의 순수납액이며 이익·발생주의 매출·장기 유지효과와 동일시하지 않는다.

## 6. Booking Sync Recovery Guardrail

### 원칙 A — 외부 예약 접수와 내부 동기화를 분리한다

`booking_received_at`이 존재하지만 `booking_synced_at`이 없으면 예약이 사라졌다고 단정하지 않는다. `PENDING`으로 두고 복구 후 재대조한다.

### 원칙 B — 실패 요청은 무조건 성공으로 간주하지 않는다

API 실패 또는 점검시간 중 변경요청은 `FAILED/PENDING` 상태를 남긴다. 재시도 결과가 확인되기 전에는 재고·시간·휴무일이 반영됐다고 기록하지 않는다.

### 원칙 C — 복구 후 전체 대조한다

점검·장애 종료 후 다음을 비교한다.

1. 외부 플랫폼의 해당 기간 신규 예약
2. 내부 운영시스템의 동일 기간 신규 예약
3. 취소·시간변경·인원변경
4. 반별 실제 체험 허용석
5. 중복 생성 또는 누락 의심 건
6. 담당자 확인 완료 여부

### 원칙 D — 복구 과정에서 고객 메시지를 중복 발송하지 않는다

예약확인·리마인드 발송은 `booking_synced`와 `message_sent` 상태를 함께 확인한다. 장애 복구를 이유로 같은 고객에게 확인 메시지를 두 번 보내지 않는다.

### 원칙 E — 기존회원 수업품질을 위해 체험 밀도를 별도 관리한다

현재 2026년 9월 유도장 운영사례에서도 신규 체험을 무제한으로 한 수업에 넣지 않는 구조가 확인된다.

- Kokushikai Judo Academy는 현행 일정에서 `보통 한 수업당 체험학생 1명`을 원칙으로 안내하고, 친구·형제자매에는 예외를 둘 수 있다고 명시한다. [J1]
- Mike's Judo Club의 2026년 9월 시간표는 일부 수업을 `FULL`로 표시하면서 다른 초보반에는 `Free Trial / Book`을 따로 제공한다. [J2]
- St Albans Judo Club은 현재 유소년 체험에 대기목록을 운영하며, 성인 초보자는 2026-09-17 별도 입문과정을 안내한다. [J3]

따라서 `safe_capacity`와 `trial_capacity`를 같은 값으로 두지 않는다. 체험생이 안전정원 안에 들어간다고 해서 기존회원 수업품질까지 자동으로 보장되는 것은 아니다.

## 8. 실험 및 운영 검증

### EXP-241 — Booking Reconciliation Coverage

**가설**  
점검·장애 이후 예약 대조 절차를 적용하면 `외부 접수는 존재하지만 내부에서 확인되지 않은 예약`을 미확인 상태로 방치하는 위험을 줄일 수 있다.

**측정**
- booking_received 수
- booking_synced 수
- PENDING/FAILED 수
- reconciliation 완료 수
- 중복·누락 의심 수
- 해당 예약의 verified_attendance 수

**성공 판단**
- 점검·장애가 있었던 관찰구간의 모든 예약이 `SYNCED / CANCELLED / DUPLICATE_CONFIRMED / MANUAL_REVIEW` 중 하나로 최종 분류됨
- `UNKNOWN`을 임의로 0건 처리하지 않음

**중단/수정 조건**
- 복구 작업이 예약 중복생성 또는 고객 중복연락을 유발
- 내부 시스템이 원천 플랫폼보다 오래된 상태를 원본으로 덮어씀
- 대조 과정에서 개인식별정보를 공개 문서나 공개 로그에 저장

### EXP-242 — Trial Density Guardrail

**가설**  
`안전정원`과 별도로 `체험 허용석`을 관리하면 신규 체험기회를 유지하면서 기존회원 수업밀도와 코치 지도부담을 함께 관리할 수 있다.

**주 KPI**
- 반별 normal_member_attendance
- confirmed_trial_count
- trial_to_verified_attendance
- trial_to_paid_within_14d
- 기존회원 수업불편/혼잡 신고 건수
- 코치 추가 설명·배치시간
- 30일 활성
- 재등록

**성공/확대 원칙**
- 단순 체험예약 증가가 아니라 실방문·30일 활성과 기존회원 경험을 함께 확인한다.
- 적정 체험석 수는 외부 도장의 `1명`을 그대로 복사하지 않고 파이널유도의 공간·코치수·회원구성 데이터로 결정한다.

**중단 조건**
- 안전정원 초과
- 기존회원의 실제 수업시간·파트너링·지도품질 저하
- 코치가 신규 체험 대응 때문에 정규회원 지도를 지속적으로 놓침
- 체험예약은 늘지만 실방문·등록·30일 활성에 개선 없음

기준선, 허용 체험석 수, 코치 추가시간, 최소 개선폭, 표본수는 모두 **데이터 미연결**이다.

## 9. 적용 전 인수검증 시나리오

아래는 합격 조건이며 실제 운영시스템에서 실행한 테스트 결과가 아니다.

1. 플랫폼 이용완료이지만 출석 증거 없음 → UNKNOWN, 방문 성공 처리 금지.
2. 미래 수업 예약 → 이번 종료 코호트에서 제외.
3. 같은 참가자·회차의 중복 기록 → 한 번만 집계.
4. 일정 변경 → 변경 전 회차 이관 처리, 새 예정일 기준 재판정.
5. 가족 대리예약 → 예약자 1명을 체험자 전체로 오인하지 않음.
6. 분모 0 또는 출석 미확인 있음 → 계산 보류.
7. 기존회원·복귀회원 → 신규 첫 체험 등록률에서 분리.
8. 알림 설정만 있음 → 전달·열람 완료로 기록하지 않음.
9. 점검 중 외부 예약 접수, 내부 미확인 → PENDING 후 복구 대조.
10. API 실패한 휴무일 변경 → 재시도 성공 확인 전 반영 완료 처리 금지.
11. 복구 후 동일 예약 2건 생성 → 중복 확인 후 한 참가자-회차로 정리.
12. 안전정원은 남았으나 체험 허용석 소진 → 대체시간 또는 대기목록으로 라우팅.

## 10. 필요한 대표 승인·입력

현재 모두 **데이터 미연결**이다.

- 네이버 예약 실제 사용 여부
- 자체 앱/외부 예약과 네이버 사이의 현재 연동 방식
- API 또는 수동 동기화 여부
- 지점별 안전정원
- 반별 정상회원 평균 실출석
- 반별 체험 허용석
- 코치 1인당 실제 관리 가능한 수업밀도
- 예약확인·리마인드 발송 시스템과 중복방지 방법
- 예약→실방문→등록→30일 활성 전환
- 기존회원 불편·혼잡 관련 기록 방식

## 13. 이번 회차 결론

현재 파이널유도에서 신규 체험 전환을 높이려면 광고를 하나 더 추가하기 전에 `예약이 실제로 접수됐는가 → 내부에서 확인됐는가 → 장애 후 누락 없이 대조됐는가 → 해당 반에 체험생을 넣어도 기존회원 경험이 보호되는가 → 실제 방문했는가`를 한 체인으로 관리해야 한다.

네이버의 2026-09-09 공식 점검 공지는 고객 예약과 사업자 관리/API 상태가 일시적으로 분리될 수 있음을 명확히 보여준다. 동시에 현재 유도장 사례는 신규 체험을 무제한 수용하지 않고 별도 체험석·만석·대기목록을 운영하는 구조를 보여준다.

파이널유도의 실제 예약수, 미동기화 건수, 체험 허용석, 회원수, 전환율, 매출은 모두 **데이터 미연결**이다. 이 문서는 실제 장애 발생 또는 성과 개선을 주장하는 문서가 아니라, 검증 가능한 복구·계측·수업품질 보호 규격이다.

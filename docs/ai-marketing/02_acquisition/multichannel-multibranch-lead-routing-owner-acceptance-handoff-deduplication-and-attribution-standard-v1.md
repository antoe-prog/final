# 다채널·다지점 문의 라우팅·담당자 수락·인계·중복 제거·전환 귀속 기준 v1

- 문서 상태: 공개 가능한 운영 기준 초안
- 기준일: 2026-09-19
- 적용 범위: 네이버·Instagram·당근·웹폼·전화·방문 문의, 신규 체험·휴면복귀·재등록 문의, 지점 간 인계
- 제외 범위: 실제 이름·연락처·대화 원문·회원 상태·개인별 출석·건강·결제 원장, 내부 가격·손익, 미확정 행사, 승인 대기 Instagram 콘텐츠

## 1. 목적

한 사람이 여러 채널 또는 여러 지점으로 같은 질문을 보내면 문의 레코드가 중복 생성될 수 있다. 반대로 채널 계정에 메시지가 도착했더라도 담당자에게 배정되지 않거나, 배정 후 담당자가 수락하지 않거나, 답변이 실제로 전달되지 않을 수 있다.

이 기준은 다음 오류를 방지한다.

1. 메시지 수신을 사람 응답으로 계산하는 오류
2. 담당자 배정을 담당자 수락으로 계산하는 오류
3. 자동응답을 상담 완료로 계산하는 오류
4. 같은 문의를 채널·지점별 신규 리드로 중복 계산하는 오류
5. 지점 인계를 신규 문의·신규회원·신규 매출로 다시 계산하는 오류
6. 예약 의향·링크 클릭·폼 제출을 체험 또는 등록으로 승격하는 오류
7. 최초 접점과 실제 전환 기여를 구분하지 않는 오류

## 2. 핵심 객체

| 객체 | 식별자 | 설명 |
|---|---|---|
| 사람 | `person_id` | 실제 문의·참여 주체 |
| 문의 | `inquiry_id` | 같은 목적의 문의 묶음 |
| 접점 | `touchpoint_id` | 채널별 수신·발신 사건 |
| 대화 | `conversation_id` | 채널 내 연속 메시지 묶음 |
| 라우팅 | `routing_id` | 지점·담당자 배정 결정 |
| 담당 업무 | `task_id` | 담당자의 수락·처리 대상 |
| 인계 | `handoff_id` | 지점·담당자 변경 기록 |
| 예약 | `booking_id` | 체험·방문 예약 요청과 확정 |
| 체험 | `trial_id` | 실제 체험 자격·참여 기록 |
| 회원권 | `membership_id` | 활성화된 이용권 |
| 결제 | `payment_id` | 승인·실수납·환불·차지백 |
| 지점 | `location_id` | 서비스 제공 및 담당 지점 |
| 캠페인 | `campaign_id` | 콘텐츠·광고·프로모션 단위 |

사람, 문의, 접점, 대화는 같은 객체가 아니다. 한 문의가 세 채널에서 반복되어도 문의는 하나일 수 있고, 한 사람이 다른 목적의 문의를 여러 번 할 수도 있다.

## 3. 문의 유형

최소한 다음 목적을 구분한다.

- 신규 체험 문의
- 체험 일정 변경·취소
- 체험 후 등록 문의
- 휴면회원 복귀 문의
- 만료예정·재등록 문의
- 기존회원 수업·운영 문의
- 가격·환불·결제 문의
- 불만·건의·안전 사건
- 채용·제휴·영업 문의
- 스팸·무관 문의

불만·안전·개인정보·아동보호 사건은 일반 마케팅 리드에서 분리해 승인된 긴급 이관 절차로 보낸다.

## 4. 채널 수신 상태

- `MESSAGE_RECEIVED`: 채널에 메시지가 도착함
- `AUTO_ACK_SENT`: 자동 수신 확인이 발송됨
- `DELIVERY_CONFIRMED`: 시스템상 전달이 확인됨
- `READ_DETECTED`: 플랫폼상 읽음 신호가 있음
- `HUMAN_REVIEWED`: 사람이 내용을 확인함
- `HUMAN_RESPONSE_DRAFTED`: 사람이 답변 초안을 작성함
- `HUMAN_RESPONSE_APPROVED`: 필요한 승인을 통과함
- `HUMAN_RESPONSE_SENT`: 사람 답변이 발송됨
- `PERSON_REPLIED`: 문의자가 다시 응답함

자동 수신 확인, 전달, 읽음은 사람 검토·사람 답변·문의자 응답을 의미하지 않는다.

## 5. 라우팅 상태

- `ROUTING_PENDING`
- `LOCATION_CANDIDATE`
- `LOCATION_VERIFIED`
- `OWNER_CANDIDATE`
- `OWNER_ASSIGNED`
- `OWNER_NOTIFIED`
- `OWNER_ACCEPTED`
- `OWNER_DECLINED`
- `REASSIGNMENT_REQUIRED`
- `HANDOFF_REQUESTED`
- `HANDOFF_ACCEPTED`
- `HANDOFF_COMPLETED`
- `ROUTING_CLOSED`

`OWNER_ASSIGNED`는 시스템상 배정일 뿐이다. 담당자가 확인하고 책임을 수락한 `OWNER_ACCEPTED`와 구분한다. 인계 역시 요청·수락·완료를 분리한다.

## 6. 지점 라우팅 기준

### 6.1 사용 가능한 신호

- 문의자가 직접 선택한 지점
- 승인된 지점별 서비스 지역
- 실제 프로그램 운영 여부
- 참여 대상·연령·수업 유형
- 예약 가능한 정원
- 문의자가 제시한 방문 가능 조건

### 6.2 자동 확정에 사용하지 않는 신호

- IP 위치
- 소셜 프로필의 추정 위치
- 전화번호 지역번호만의 추정
- 검색 키워드 또는 해시태그
- 최근 본 게시물
- 보호자·지인의 지점 이력

지점이 명확하지 않으면 후보 상태로 유지한다. 위치 추정만으로 지점을 확정하거나 고객 정보를 다른 지점에 공유하지 않는다.

## 7. 담당자 배정 기준

배정 규칙은 대표가 승인한 운영시간·지점·업무 유형·대체 담당자를 사용한다.

1. 긴급 사건 여부 확인
2. 문의 목적 분류
3. 지점 확인
4. 담당 역할 확인
5. 근무·처리 가능 상태 확인
6. 기존 담당자·대화 이력 확인
7. 중복 업무 확인
8. 담당자 배정
9. 담당자 통지
10. 담당자 수락 확인

배정 후 정해진 기간 내 수락이 없으면 `REASSIGNMENT_REQUIRED`로 전환한다. 실제 시간 기준은 추정하지 않고 대표 승인값을 사용한다.

## 8. 중복 탐지와 병합

### 8.1 중복 후보 신호

- 동일한 승인된 연락 식별자
- 가까운 시간에 같은 목적·지점·참여자 조건
- 동일 예약·문의 참조번호
- 사용자가 스스로 같은 문의라고 밝힌 경우

### 8.2 자동 병합 금지

다음 하나만으로 병합하지 않는다.

- 같은 이름
- 같은 성씨
- 같은 주소·학교·회사
- 같은 보호자 또는 결제자
- 같은 IP·기기
- 비슷한 문의 문장
- 같은 SNS 게시물에 반응

### 8.3 병합 절차

1. `DUPLICATE_CANDIDATE` 표시
2. 원본 문의와 후보 문의 비교
3. 사람 검토
4. 유지할 기준 레코드 결정
5. 채널·대화·지점·담당자·상태 이력 보존
6. 병합 승인
7. 중복 후속 업무 취소
8. 병합 로그 기록

병합은 되돌리기 어려울 수 있으므로 승인 권한을 제한하고 원본 ID와 병합 시각을 보존한다.

## 10. 응답시간 측정

### 10.1 시각 필드

- `received_at`: 유효 문의 수신 시각
- `validated_at`: 스팸·중복 기본 검토 완료 시각
- `assigned_at`: 담당자 배정 시각
- `accepted_at`: 담당자 수락 시각
- `first_human_response_sent_at`: 최초 사람 답변 발송 시각
- `first_person_reply_at`: 문의자의 첫 후속 응답 시각
- `resolved_at`: 문의 목적이 처리된 시각

### 10.2 지표

- 배정시간 = `assigned_at - validated_at`
- 수락시간 = `accepted_at - assigned_at`
- 최초 사람응답시간 = `first_human_response_sent_at - received_at`
- 연결시간 = `first_person_reply_at - received_at`
- 처리시간 = `resolved_at - received_at`

운영시간 외 문의, 스팸, 중복 확정, 시스템 장애, 승인 대기 사건은 별도 큐로 분리한다. 자동응답 시각을 사람응답시간으로 사용하지 않는다.

## 11. 인계 기준

### 11.1 인계 사유

- 문의자가 다른 지점을 명시함
- 대상 프로그램이 다른 지점에서만 운영됨
- 정원·운영시간 조건 불일치
- 담당자 권한 부족
- 불만·안전·개인정보 사건 이관
- 담당자 부재 또는 수락 거절

### 11.2 인계에 포함할 최소 정보

- `inquiry_id`
- 문의 목적
- 확인된 지점·프로그램 조건
- 현재 상태
- 완료된 응답과 남은 업무
- 연락 자격과 수신거부 상태
- 다음 담당자와 수락 기한

실제 개인정보는 승인된 내부 시스템에서 최소 범위로 전달한다. 공개 저장소·개인 메모·공개 채팅으로 복사하지 않는다.

### 11.3 인계 완료 조건

다음 담당자가 수락하고 필요한 맥락을 확인한 뒤에만 완료한다. 보낸 쪽이 전달 버튼을 누른 사실만으로 인계 완료로 처리하지 않는다.

## 12. 채널별 실행 기준

### 네이버

- 플레이스·블로그·예약·톡톡 등 유입 경로를 구분한다.
- 같은 사람이 여러 기능을 이용해도 문의 목적이 같으면 중복 후보로 검토한다.
- 게시물 조회·저장·지도 클릭을 유효 문의로 계산하지 않는다.

### Instagram 코치 개인 계정

- 코치 개인의 콘텐츠 질문과 도장 체험·운영 문의를 구분한다.
- 댓글·좋아요·팔로우를 상담·예약으로 계산하지 않는다.
- 공식 지점 정책을 코치 개인이 확정한 것처럼 답변하지 않는다.
- 회원·보호자·미성년자 식별정보를 DM에서 공개 콘텐츠로 옮기지 않는다.

### 당근·지역 커뮤니티

- 광고·비즈프로필·채팅·댓글을 별도 접점으로 기록한다.
- 공개 댓글에서 연락처·건강·결제정보를 요청하지 않는다.
- 지점과 운영 프로그램이 확인되지 않으면 예약 가능성을 약속하지 않는다.

### 전화·방문

- 부재중 전화·통화 시도·실제 연결을 분리한다.
- 방문 질문·시설 견학·체험 참여를 별도 사건으로 기록한다.
- 구두 문의도 동일한 `inquiry_id`와 담당자 수락 기준을 적용한다.

## 13. 목표별 활용

### 신규 체험회원 확보

- 유효 문의 → 지점 확인 → 담당자 수락 → 사람 연결 → 체험 예약 → 실제 참여를 분리한다.
- 콘텐츠·채널별로 문의량뿐 아니라 실제 참여까지 추적한다.

### 휴면회원 복귀

- 신규 문의와 휴면복귀 문의를 구분한다.
- 기존 회원권·출석 상태가 확인되기 전 신규회원으로 분류하지 않는다.
- 복귀 예약과 실제 복귀·재등록을 분리한다.

### 기존회원 재등록·만족

- 운영 문의·불만·만료예정 문의를 신규 리드 큐에서 분리한다.
- 담당자 변경 시 사건·약속·해결 상태를 인계한다.
- 답변 발송을 해결·만족·재등록으로 계산하지 않는다.

### 매출 증대

- 문의·예약·의향이 아니라 실수납과 회원권 활성 후 귀속한다.
- 지점 인계 시 최초 접점과 실제 서비스·수납 지점을 별도 기록한다.
- 환불·차지백·지점 이동의 중복 귀속을 차단한다.

## 14. 귀속 모델

| 귀속 | 기준 |
|---|---|
| 최초 접점 | 최초 유효 문의를 만든 `touchpoint_id` |
| 최신 접점 | 전환 전 마지막 유효 접점 |
| 상담 담당 | 최초 사람 연결을 완료한 담당자 |
| 예약 담당 | 예약 확정을 완료한 담당자 |
| 서비스 지점 | 실제 체험·수업이 제공된 지점 |
| 수납 지점 | 기준 원장상 실수납이 귀속된 지점 |
| 보조 기여 | 승인된 규칙에 따라 기록하되 중복 매출 금지 |

하나의 결제를 여러 지점·담당자·채널에 전액 중복 귀속하지 않는다. 기여 보고와 회계 매출을 같은 값으로 취급하지 않는다.

## 15. KPI 정의

| KPI | 분자 | 분모 |
|---|---|---|
| 유효 문의율 | 유효 문의 수 | 전체 수신 문의 수 |
| 담당자 수락률 | 수락된 업무 수 | 배정된 업무 수 |
| 사람 연결률 | 문의자 응답이 확인된 문의 수 | 사람 답변 발송 문의 수 |
| 체험 예약률 | 확정 예약 참여자 수 | 체험 적격 참여자 수 |
| 체험 실참여율 | 실제 체험 참여자 수 | 확정 예약 참여자 수 |
| 등록 활성률 | 회원권 활성 참여자 수 | 실제 체험 참여자 수 |
| 중복률 | 중복 확정 문의 수 | 유효 문의 후보 수 |
| 인계 성공률 | 수락·완료된 인계 수 | 인계 요청 수 |
| 순수납 | 실수납 - 완료 환불 - 차지백 | 해당 기간 |

분모가 0이거나 데이터가 연결되지 않으면 계산하지 않는다.

## 16. 자동화 전 필수 게이트

4. 중복 후보 검토가 끝났는가

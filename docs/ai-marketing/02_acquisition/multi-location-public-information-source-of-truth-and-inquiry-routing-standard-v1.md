# 다지점 공개정보 원본·정합성·문의 귀속 기준 v1

- 문서 상태: 공개 운영 기준 초안
- 작성일: 2026-09-15 (Asia/Seoul)
- 적용 범위: 본관 및 운영이 확인된 각 지점의 Google Business Profile, 네이버 플레이스, 당근 비즈프로필, 공식 웹사이트·앱, 공개 SNS
- 제외 범위: 미확정 지점, 내부 연락처, 회원·보호자 정보, 개인별 문의 내용, 미승인 시간표·가격·혜택·행사

## 1. 목적

지역 검색에서 도장을 발견한 사람이 다른 채널로 이동했을 때 지점명, 주소, 운영시간, 수업 정보, 문의 경로가 달라 이탈하는 문제를 예방한다.

이 기준은 다음 흐름을 하나의 측정 가능한 퍼널로 연결한다.

`지역 검색 노출 → 지점 정보 확인 → 문의 경로 선택 → 유효 문의 → 체험 예약 → 실제 참석 → 등록 → 순수납`

노출·클릭·전화 버튼 탭은 문의나 예약이 아니다. 문의와 예약도 실제 참석·등록·매출이 아니다.

## 2. 핵심 원칙

### 2.1 지점별 공개정보 원본은 하나다

- 각 지점은 승인된 `LOCATION_MASTER` 레코드 하나를 가진다.
- 채널별 문구는 달라도 사실 필드는 이 원본에서 파생한다.
- 실제 원본과 다른 채널 정보를 발견하면 임의 수정하지 않고 충돌로 기록한다.
- 원본이 연결되지 않은 값은 `데이터 미연결`로 표시한다.

### 2.2 본관과 각 지점을 섞지 않는다

- 주소, 전화, 길찾기, 운영시간, 시간표, 담당 역할은 지점 단위로 관리한다.
- 중앙 문의를 쓰더라도 최종 귀속 지점과 인계 상태를 별도 기록한다.
- 다른 지점의 후기·사진·시간표를 현재 지점의 정보처럼 재사용하지 않는다.

### 2.3 영업시간과 수업시간표를 구분한다

- `영업시간`은 고객 응대 또는 방문 가능한 운영시간이다.
- `수업시간표`는 프로그램·대상·회차별 실제 수업시간이다.
- 수업시간 일부만 보고 영업시간을 만들거나 반대로 영업시간을 수업시간으로 안내하지 않는다.
- 공휴일·임시휴관·행사 운영은 상시시간을 덮어쓰지 않고 별도 유효기간을 둔다.

### 2.4 코치 개인 계정은 지점 공식 원본이 아니다

- `@ant.toe.98`은 코치 개인 계정으로 운영한다.
- 확인된 링크를 넣더라도 코치 콘텐츠의 방문자를 검증된 문의 경로로 안내하는 보조 접점이다.
- 지점의 공식 시간표·가격·환불·혜택·행사를 개인 계정이 독자적으로 확정하거나 발표하지 않는다.

## 4. 필드 상태

| 상태 | 의미 | 공개 사용 |
|---|---|---|
| `UNCONNECTED` | 원천이 연결되지 않음 | 금지 |
| `CLAIMED` | 담당자가 값을 입력했으나 증거 미검토 | 금지 |
| `VERIFIED` | 승인된 원천과 대조 완료 | 허용 |
| `CHANNEL_PENDING` | 채널 변경 제출 후 검토 중 | 기존 공개값과 혼합 금지 |
| `LIVE_VERIFIED` | 실제 공개 화면에서 반영 확인 | 허용 |
| `CONFLICT` | 원본·채널 또는 채널 간 값 불일치 | 신규 배포 보류 |
| `EXPIRED` | 검증 유효기간 경과 | 재검증 전 신규 배포 보류 |
| `RETIRED` | 이전·폐점 등으로 더 이상 사용하지 않음 | 신규 유입 경로에서 제외 |

## 5. 채널별 책임

### 5.1 Google Business Profile

- 실제 장소별로 중복되지 않는 프로필을 사용한다.
- 현실의 간판·표기와 일치하는 지점명을 사용한다.
- 주소와 지도 핀을 실제 방문 위치에 맞춘다.
- 가능하면 해당 지점으로 연결되는 전화번호와 웹페이지를 사용한다.
- 다지점의 기본 카테고리는 실제 핵심 사업을 반영하도록 일관되게 관리한다.
- 정규시간과 공휴일·임시변경을 구분한다.
- 변경 제출과 실제 공개 반영을 별도 상태로 기록한다.

### 5.2 네이버 플레이스

- 업체 정보 수정 화면의 지점명·주소·전화·영업시간을 `LOCATION_MASTER`와 대조한다.
- 플레이스의 길찾기 도착점과 실제 출입구를 확인한다.
- 프로그램별 시간표가 상시 영업시간처럼 보이지 않도록 문구를 분리한다.
- 변경 검토 중에는 반영 완료로 보고하지 않는다.

### 5.3 당근 비즈프로필

- 동네와 실제 운영 지점을 일치시킨다.
- 소식·채팅·쿠폰·예약은 서로 다른 사건으로 집계한다.
- 쿠폰·예약 기능이 보인다는 이유만으로 실제 혜택 또는 예약 가능 상태로 표시하지 않는다.
- 여러 지점 브랜드 기능은 실제 입점·승인 상태를 확인한 뒤 사용한다.

### 5.4 공식 웹사이트·앱

- 지점별 고유 URL 또는 식별 가능한 경로를 둔다.
- 지점명·주소·문의 경로·운영 상태를 `LOCATION_MASTER`에서 가져온다.
- 지점 페이지가 도시명만 바꾼 중복 문서가 되지 않도록 실제 코치·시설·프로그램 등 검증된 차이를 사용한다.
- 문의 완료 뒤 사용자가 선택한 지점과 최종 배정 지점을 모두 기록한다.

### 5.5 Instagram `@ant.toe.98`

- 계정 주체는 코치 개인으로 유지한다.
- 링크 추가 전 도착 URL, 공개 가능성, 담당 역할, 지점 선택 방식을 검증한다.
- 게시물 CTA는 한 가지로 제한한다.
- 링크가 없거나 미검증이면 `수업 문의 ↓` 같은 표현을 추가하지 않는다.
- 프로필 방문과 링크 클릭을 체험 문의로 계산하지 않는다.

## 6. 정합성 규칙

### 6.1 반드시 일치해야 하는 필드

- 공개 지점명
- 도로명주소와 상세 위치
- 문의 전화 또는 승인된 중앙 문의 표기
- 운영 상태
- 영업시간의 기준일
- 공휴일·임시변경의 유효기간
- 문의 URL의 최종 도착지

### 6.2 채널별로 달라도 되는 필드

- 소개문의 길이와 형식
- 사진 배열
- 콘텐츠 주제
- CTA 문구
- 플랫폼이 지원하는 속성

달라도 되는 필드 역시 사실의 강도는 원본을 넘지 못한다.

## 7. 변경 절차

`CHANGE_REQUESTED → SOURCE_VERIFIED → OWNER_APPROVED → CHANNEL_SUBMITTED → LIVE_VERIFIED → MEASUREMENT_HANDOFF`

### 7.1 CHANGE_REQUESTED

- 변경 사유와 대상 지점을 기록한다.
- 변경할 필드와 영향을 받는 채널을 나열한다.

### 7.2 SOURCE_VERIFIED

- 계약·현장·운영표·담당자 등 승인된 원천과 대조한다.
- 가격·혜택·행사는 별도 승인 객체가 없으면 제외한다.

### 7.3 OWNER_APPROVED

- 대표 또는 위임된 역할이 정확한 값을 승인한다.
- 승인 범위를 다른 지점이나 후속 변경에 확대하지 않는다.

### 7.4 CHANNEL_SUBMITTED

- 실제 채널 변경을 제출한 시각과 작업자를 기록한다.
- 플랫폼 검토 중인 값을 공개 완료로 간주하지 않는다.

### 7.5 LIVE_VERIFIED

- 로그아웃 또는 일반 방문자 화면에서 지점명·주소·시간·링크를 확인한다.
- 지도 핀과 문의 도착 경로를 직접 검사한다.

### 7.6 MEASUREMENT_HANDOFF

- 변경 전 기준시각과 변경 후 관찰시점을 기록한다.
- 테스트 문의에는 `TEST`를 표시해 실제 KPI에서 제외한다.

## 8. 문의 귀속 상태

| 코드 | 판정 |
|---|---|
| `PROFILE_VIEW` | 프로필 또는 지점 페이지 조회 |
| `CONTACT_ACTION` | 전화·채팅·링크 버튼 실행 |
| `INQUIRY_RECEIVED` | 실제 메시지·통화·폼 제출 수신 |
| `INQUIRY_VALIDATED` | 사람·목적·지점 의사가 확인된 유효 문의 |
| `LOCATION_SELECTED` | 문의자가 희망 지점을 선택 |
| `LOCATION_ASSIGNED` | 운영자가 응대 지점을 배정 |
| `HANDOFF_ACCEPTED` | 해당 지점 담당자가 인계를 수락 |
| `TRIAL_BOOKED` | 날짜·회차가 확정된 체험 예약 |
| `TRIAL_ATTENDED` | 실제 참석 증거 확인 |
| `MEMBERSHIP_STARTED` | 계약 효력 시작 확인 |
| `NET_COLLECTION_VERIFIED` | 환불·취소 등을 반영한 순수납 확인 |

`CONTACT_ACTION`은 `INQUIRY_RECEIVED`가 아니다. 중앙 문의에서 지점으로 전달했더라도 `HANDOFF_ACCEPTED` 전에는 지점 응답으로 계산하지 않는다.

## 9. 귀속 파라미터

개인정보 없이 다음 식별자를 사용할 수 있다.

- `source_channel`: google, naver, daangn, instagram, website, app, offline
- `source_surface`: profile, post, map, bio, qr, direct
- `source_location_id`: 승인된 비식별 지점 코드
- `campaign_id`: 승인된 캠페인 코드
- `content_id`: 공개 콘텐츠 작업 ID
- `first_touch_at`: 최초 접점 시각
- `inquiry_received_at`: 실제 문의 수신 시각
- `assigned_location_id`: 최종 배정 지점 코드
- `handoff_status`: pending, accepted, rejected, rerouted

전화·채팅에서 출처를 확인할 수 없으면 `unknown`으로 두며 직원이 임의로 Instagram이나 광고에 귀속하지 않는다.

## 10. KPI 정의

분자·분모·기간·원천이 모두 있을 때만 계산한다.

### 10.1 공개정보 완전율

`LIVE_VERIFIED 필수 필드 수 ÷ 공개 대상 필수 필드 수`

### 10.2 채널 정합률

`LOCATION_MASTER와 일치하는 검증 필드 수 ÷ 검토한 채널 필드 수`

### 10.3 문의 도착률

`INQUIRY_RECEIVED 수 ÷ CONTACT_ACTION 수`

버튼 실행 데이터가 없는 채널은 계산하지 않는다.

### 10.4 지점 인계 완료율

`HANDOFF_ACCEPTED 수 ÷ LOCATION_ASSIGNED 수`

### 10.5 유효 문의→체험 예약률

`TRIAL_BOOKED 수 ÷ INQUIRY_VALIDATED 수`

### 10.6 체험 참석·등록·순수납

- 체험 참석률: `TRIAL_ATTENDED ÷ TRIAL_BOOKED`
- 신규 시작률: `MEMBERSHIP_STARTED ÷ 관찰기간이 끝난 TRIAL_ATTENDED`
- 순수납 기여: 환불·취소·차지백을 반영한 실제 수납 합계

현재 내부 원천이 연결되지 않았으므로 모두 `데이터 미연결`이다.

## 11. 60분 비식별 감사 절차

1. 운영이 확인된 지점 목록과 `LOCATION_MASTER` 존재 여부를 확인한다.
2. 각 지점의 Google·네이버·당근·웹 URL을 수집한다.
3. 지점명·주소·전화·시간·운영상태·문의 URL을 표로 대조한다.
4. 지도 핀과 실제 출입구를 확인한다.
5. 중앙 문의와 지점 직접 문의의 인계 방식을 확인한다.
6. `CONFLICT`, `EXPIRED`, `UNCONNECTED`를 우선순위별로 분류한다.
7. 대표 승인 전에는 채널 값을 수정하지 않는다.
8. 승인 후 한 채널씩 제출하고 실제 공개 화면을 재검증한다.

### P2

- 출처 파라미터가 없어 문의 귀속이 불명확함

## 13. 실험 EXP-318

### 가설

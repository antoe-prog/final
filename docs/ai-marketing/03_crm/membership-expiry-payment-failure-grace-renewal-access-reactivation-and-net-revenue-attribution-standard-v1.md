# 회원권 만료·결제 실패·유예·재등록·이용권한·순수납 귀속 기준 v1

- 목적: 회원권 종료 전후의 상태를 정확히 구분해 기존회원 만족·재등록·복귀·매출 성과를 과장 없이 관리한다.
- 적용 범위: 만료예정, 자동갱신, 수동갱신, 결제 실패, 결제 재시도, 유예, 휴회, 취소, 만료, 재활성화, 이용권한, 환불·차지백.
- 공개 범위: 운영 원칙과 비식별 상태 정의만 포함한다.
- 제외: 실제 회원·보호자 정보, 연락처, 개인별 계약·출석·결제 원장, 가격, 지점별 내부 목표, 메시지 발송 대상.
- 작성·공개 검토: 2026-09-20 KST.

## 1. 핵심 판단

회원권 만료와 결제 실패를 곧바로 이탈로 계산하지 않는다. 재등록 성과는 최소한 `계약 효력`, `이용권한`, `실제 정산`을 분리해 확인한다.

운영 퍼널은 다음 순서로 관리한다.

`만료예정 또는 갱신예정 → 안내 승인 → 발송 → 사람의 응답 → 갱신 의사 → 계약 효력 → 결제 시도 → 실정산 → 이용권한 → 실제 참여 → 환불·차지백 반영`

각 단계는 다음 단계를 자동으로 증명하지 않는다.

- 만료예정 알림 발송은 재등록이 아니다.
- 자동갱신 예정은 계약 연장 완료가 아니다.
- 결제 시도·승인은 실정산이 아니다.
- 결제 실패는 취소나 이탈 확정이 아니다.
- 결제 재시도 예약은 결제 회수가 아니다.
- 결제 완료만으로 프로그램·회차·지점 이용권한이 정상이라고 단정하지 않는다.
- 첫 복귀 출석만으로 신규등록과 재등록을 동시에 계산하지 않는다.
- 환불·차지백 전 금액을 최종 순수납으로 보고하지 않는다.

## 2. 상태를 분리해 기록한다

### 2.1 회원권·계약 상태

| 상태 | 의미 | 성과로 계산하지 않는 항목 |
|---|---|---|
| `pending` | 시작 전 또는 승인 대기 | 활성회원·재등록 |
| `active` | 현재 효력 확인 | 실제 출석·실정산 |
| `ending_scheduled` | 종료 예정일 존재 | 실제 만료·이탈 |
| `renewal_pending` | 갱신 절차 진행 중 | 재등록 완료 |
| `renewed_effective` | 갱신 효력 확인 | 실정산·실제 참여 |
| `frozen` | 승인된 휴회 | 취소·이탈 |
| `expired` | 종료일 경과와 효력 종료 확인 | 영구 이탈 |
| `canceled` | 취소 효력 확인 | 환불 완료 |
| `reactivated` | 과거 종료 뒤 새 효력 시작 | 신규등록 |

### 2.2 결제 상태

| 상태 | 의미 | 성과로 계산하지 않는 항목 |
|---|---|---|
| `scheduled` | 미래 청구 예정 | 결제 시도·수납 |
| `attempted` | 결제 시도 발생 | 승인·실정산 |
| `authorized` | 승인 또는 승인 대기 | 최종 수납 |
| `failed` | 시도 실패 | 취소·이탈 |
| `retry_scheduled` | 재시도 예정 | 회수 완료 |
| `settled` | 승인된 원장에서 수납 확인 | 환불 반영 후 순수납 |
| `refunded` | 환불 완료 | 순수납 유지 |
| `chargeback` | 차지백 반영 | 순수납 유지 |

### 2.3 이용권한 상태

| 상태 | 의미 |
|---|---|
| `not_started` | 효력 시작 전 |
| `allowed` | 프로그램·회차·지점 이용 가능 확인 |
| `limited` | 승인된 범위로 제한 |
| `suspended` | 일시 중단 |
| `expired` | 이용권한 종료 |
| `error_review` | 계약·결제와 불일치해 사람 검토 필요 |

결제 원장에 반복 청구가 존재해도 회원권과 연결되지 않은 별도 청구라면 이용권한의 근거로 쓰지 않는다.

### 2.4 연락 상태

`draft → approved → sent → delivered → replied → handled`

- 초안 작성은 발송이 아니다.
- 발송은 전달이나 사람의 응답이 아니다.
- 응답은 재등록 의사·계약·실정산이 아니다.
- 광고성 메시지 여부와 수신 동의 기준은 별도 승인 정책을 따른다.

## 3. 재등록·복귀·이탈 정의

대표가 관찰창과 공식 정의를 승인하기 전에는 다음 지표를 `데이터 미연결`로 둔다.

### 3.1 계속 갱신

기존 계약의 효력이 끊기지 않고 승인된 갱신 규칙에 따라 이어진 경우다. 자동갱신 설정만 존재하거나 청구만 예정된 경우는 포함하지 않는다.

### 3.2 재등록

대표가 정한 만료 전후 관찰창 안에서 갱신 계약 효력과 실정산이 확인된 경우다. 만료예정 안내, 의사 표현, 결제 시도만으로는 계산하지 않는다.

### 3.3 복귀·재활성화

과거 효력이 실제로 종료된 뒤 새 계약 효력이 시작된 경우다. 첫 방문이나 문의만으로 복귀 완료로 계산하지 않는다.

### 3.4 이탈

단순 결제 실패, 휴회, 일정 변경, 지점 이동, 승인된 유예, 결제 재시도 중 상태를 이탈로 자동 분류하지 않는다. 공식 취소 또는 종료 효력과 관찰창 종료를 기준으로 판정한다.

### 3.5 유예

유예는 별도 운영 정책이다. 기간, 이용 가능 범위, 청구·출석 처리, 승인자, 종료 조건이 확인되지 않으면 임의로 적용하지 않는다. 유예 중 회원을 활성·휴회·이탈 가운데 하나로 중복 계산하지 않는다.

## 4. CRM 작업 대기열

실제 대상자 추출과 메시지 발송은 대표 승인 및 데이터 연결 후에만 실행한다.

| 대기열 | 필요한 근거 | 금지되는 자동 판정 |
|---|---|---|
| 만료예정 | 계약 종료일·상태 | 재등록 완료 |
| 자동갱신 예정 | 갱신 규칙·효력일 | 미래 수납 확정 |
| 결제 실패·재시도 중 | 실패 유형·재시도 상태 | 취소·이탈 |
| 결제수단 확인 필요 | 승인된 실패 사유 코드 | 고객 과실 단정 |
| 종료 예정 | 실제 종료 효력일 | 즉시 이탈 |
| 만료 후 미갱신 | 효력 종료·관찰창 | 영구 이탈 |
| 갱신 효력·미정산 | 계약과 결제 불일치 | 재등록 매출 |
| 실정산·권한 오류 | 결제와 권한 불일치 | 정상 서비스 제공 |
| 재활성화 후보 | 과거 종료·새 문의 또는 계약 | 신규회원 |

우선순위는 건강·안전 정보가 아니라 `효력 종료까지 남은 시간`, `결제 상태`, `이용권한 오류`, `사람의 응답`으로 정한다.

### 네이버·Google Business Profile

- 실제 가격, 시간표, 만료·갱신 조건은 승인된 최신 정보만 사용한다.
- 공개 게시물 반응을 개인의 재등록 의사로 해석하지 않는다.

### Instagram `@ant.toe.98`

- 코치 개인 계정의 교육형 콘텐츠와 수련 관점을 유지한다.
- 개인별 만료·미납·결제 실패를 공개 콘텐츠나 댓글에서 다루지 않는다.
- 저장·질문·수업 문의 등 콘텐츠 CTA와 재등록 성과를 직접 동일시하지 않는다.

### 당근·지역 채널

- 지역 인지도와 일반 문의 경로 안내에 사용한다.
- 공개 글 클릭이나 채팅 시작을 계약·수납으로 계산하지 않는다.

### CRM 메시지

- 서비스 안내와 광고성 메시지를 구분한다.
- 승인된 대상, 목적, 수신 동의, 빈도, 중단 요청을 확인한다.
- 한 사람이 여러 지점·회원권에 속해도 중복 발송과 중복 매출 귀속을 방지한다.

## 6. 매출 귀속

### 6.1 최소 연결키

- 비식별 사람 키
- 회원권·계약 키와 버전
- 효력 시작·종료일
- 프로그램·회차·지점 이용권한 키
- 청구서·결제·환불·차지백 키
- 갱신·복귀 분류와 기준일
- 유입·CRM 접점과 기여 규칙

### 6.2 순수납

`순수납 = 실정산 수납액 - 완료된 환불 - 차지백 - 승인된 반환액`

세금·수수료·외부기관 전달금·할인·크레딧을 어떻게 처리할지는 실제 회계 기준 승인 전까지 계산하지 않는다.

### 6.3 중복 방지

- 계속 갱신을 신규등록으로 계산하지 않는다.
- 재활성화를 신규와 재등록에 동시에 넣지 않는다.
- 업그레이드·다운그레이드 차액을 전체 재등록 매출로 계산하지 않는다.
- 여러 지점이 관여해도 사람·계약·결제 1건을 중복 합산하지 않는다.
- 결제 실패 회수액을 신규 매출과 회수 매출에 동시에 넣지 않는다.

## 8. EXP-426 — 만료·결제 실패·재등록·권한·순수납 판정 정확도

### 목적

실제 자동 연락이나 성과 보고 전에 합성 데이터로 상태 판정과 중복 방지를 검증한다.

### 합성 데이터

- 사람 600명
- 회원권·계약 900건
- 청구·결제·환불·차지백 2,700건
- 이용권한 사건 3,600건
- 안내·응답 사건 1,800건

### 성공 기준

다음 오류가 모두 0건이어야 한다.

1. 만료예정 안내를 재등록 완료로 계산
2. 결제 실패를 취소·이탈로 계산
3. 재시도 예약을 실정산으로 계산
4. 회원권과 무관한 반복 결제를 이용권한으로 계산
5. 종료 예정 상태를 실제 종료로 계산
6. 휴회를 취소 기반 이탈로 계산
7. 승인된 연장·유예를 신규등록 또는 재등록으로 중복 계산
8. 재활성화를 신규와 재등록에 중복 귀속
9. 환불·차지백을 순수납에서 누락
10. 여러 지점·계약·결제의 중복 합산
11. 수신 동의·목적이 확인되지 않은 연락 후보 생성

### 중단 기준

하나라도 실패하면 자동 대상 확정, 고객 메시지 발송, 이용권한 변경, 결제 재시도 지시, 재등록·복귀·매출 성과 보고를 중단한다.

## 10. 감사 가드레일

- 개인별 만료·미납·결제 실패를 공개 저장소나 SNS에 기록하지 않는다.
- 결제 실패 사유를 고객 과실로 단정하지 않는다.
- 승인되지 않은 가격·혜택·무료 기간·유예 기간을 만들지 않는다.
- 발송·응답·의사·계약·수납·출석을 서로 대체하지 않는다.
- Stripe 문서는 상태 설계 참고용이며 실제 결제대행사로 가정하지 않는다.
- Instagram 승인 대기 미디어·캡션과 미확정 FINAL ROAD 자료는 이 문서에 포함하지 않는다.

# 출석 공백·비활성 검토·복귀·재활성 귀속 기준 v1

- 문서 목적: 출석 공백을 곧바로 휴면·이탈로 단정하지 않고, 검토·연락 적격성·복귀 의사·예약·실제 참여·재활성을 분리해 관리한다.
- 적용 대상: 파이널유도멀티짐의 기존회원 만족, 휴면회원 복귀, 재등록과 매출 귀속 설계에 사용할 공개 가능한 표준안
- 공개 범위: 상태 정의, 역할, 채널 원칙, 측정식, 합성 실험 기준
- 제외 범위: 회원·보호자 식별정보, 연락처, 개인별 출석·건강·결제 원장, 지점별 실제 회원수·매출·전환율
- 작성일: 2026-09-16
- 내부 수치 상태: 데이터 미연결

## 1. 핵심 판단

아래 항목은 서로 같은 상태가 아니다.

`출석 공백 ≠ 비활성 확정 ≠ 휴회 ≠ 이탈 ≠ 연락 가능 ≠ 복귀 의사 ≠ 복귀 예약 ≠ 실제 복귀 ≠ 재활성 ≠ 재등록 ≠ 실수납`

최근 출석이 없다는 사실만으로 운동 중단, 불만, 가격 문제나 타 도장 이동을 추정하지 않는다. 예약하지 않았다는 사실도 휴면이나 해지 의사를 뜻하지 않는다. 복귀 의사를 밝혔거나 수업을 예약했더라도 실제 참여 전에는 복귀로 집계하지 않는다.

관리 순서는 다음과 같다.

`출석 원천 확인 → 공백 후보 탐지 → 예정된 부재·휴회·사업자 예외 제외 → 사람 검토 → 연락 적격성 확인 → 질문·장애 해소 → 복귀 예약 → 실제 복귀 참여 → 승인된 재활성 기준 → 재등록 계약 → 실수납`

## 2. 네 목표와의 연결

| 목표 | 관리할 사건 | 분리해야 할 결과 |
|---|---|---|
| 신규 체험회원 확보 | 체험 예약·참석·후속 첫 수업 | 체험 공백·미등록·신규 등록 |
| 휴면회원 복귀 | 공백 검토·복귀 의사·예약·참여 | 연락 성공·복귀 예약·실제 복귀 |
| 기존회원 재등록·만족 | 예정된 부재·휴회·문제 해결·활성 | 공백·휴회·재활성·재등록 |
| 매출 증대 | 재등록 계약·실수납·환불 | 의사·계약액·실수납·순수납 |

공백 후보를 모두 휴면회원으로 만들면 복귀 대상이 부풀려진다. 반대로 공백을 전혀 보지 않으면 일정·수업·접근권 문제를 늦게 발견할 수 있다.

## 3. 독립 상태 모델

### 3.1 출석 사건

| 코드 | 의미 | 주의점 |
|---|---|---|
| `NO_BOOKING` | 해당 기간에 예약 기록 없음 | 결석·이탈로 처리하지 않음 |
| `BOOKED` | 예약이 확인됨 | 실제 참여가 아님 |
| `ATTENDED` | 기준 출석 원천에서 실제 참여 확인 | 체크인 오류 가능성 검토 |
| `CUSTOMER_CANCELLED` | 고객 취소 원천 확인 | 사유를 추정하지 않음 |
| `BUSINESS_CANCELLED` | 도장 휴강·운영 사유 취소 | 고객 공백으로 집계하지 않음 |
| `TECH_EXCEPTION` | 예약·체크인·시스템 오류 | 고객 책임으로 처리하지 않음 |
| `ATTENDANCE_UNRESOLVED` | 원천 간 충돌 또는 확인 불가 | 확정 통계에서 분리 |

### 3.2 공백 검토

| 코드 | 의미 | 금지되는 오분류 |
|---|---|---|
| `GAP_NOT_DUE` | 승인된 검토 구간 전 | 비활성 |
| `GAP_CANDIDATE` | 출석 원천상 공백 후보 | 휴면·이탈 |
| `GAP_REVIEW` | 예약·휴회·휴강·오류를 대조 중 | 연락 대상 확정 |
| `PLANNED_ABSENCE` | 회원이 미리 알린 부재 | 이탈 |
| `APPROVED_FREEZE` | 승인된 휴회 적용 | 휴면 캠페인 대상 |
| `BUSINESS_CAUSED_GAP` | 휴강·지점 사정 등 사업자 원인 | 고객 책임 공백 |
| `CONTACT_ELIGIBILITY_REVIEW` | 연락 목적·동의·수신거부 검토 | 발송 허가 |
| `INACTIVE_CONFIRMED` | 대표 승인 정의와 근거로 비활성 확정 | 해지·불만·가격 거절 |
| `GAP_REASON_UNKNOWN` | 직접 확인된 사유 없음 | 임의 사유 코드 |

비활성 기준은 지점·상품·수업 빈도에 따라 다를 수 있다. 외부 사업자의 7일·14일·30일 기준을 파이널유도에 자동 적용하지 않는다.

### 3.3 복귀·재활성

| 코드 | 의미 |
|---|---|
| `RETURN_NOT_CONTACTED` | 연락을 실행하지 않은 상태 |
| `RETURN_CONTACT_ELIGIBLE` | 승인된 목적·전송자·채널에서 연락 가능 |
| `RETURN_QUESTION_OPEN` | 일정·수업·지점·결제·준비물 질문 미해결 |
| `RETURN_INTEREST` | 회원의 복귀 의사 확인 |
| `RETURN_BOOKED` | 복귀 수업 예약 확인 |
| `RETURN_ATTENDED` | 복귀 후 첫 실제 참여 확인 |
| `REACTIVATION_REVIEW` | 승인된 활성 기준 충족 여부 검토 |
| `REACTIVATED` | 승인된 기간·출석 조건 충족 |
| `RENEWAL_INTENT` | 재등록 의사 확인 |
| `RENEWAL_CONTRACT_CONFIRMED` | 새 계약 또는 연장 조건 확정 |
| `RENEWAL_PAYMENT_VERIFIED` | 실제 수납 확인 |

한 번 출석했다고 장기 재활성이 보장되는 것은 아니다. 반대로 승인된 복귀 참여를 새 신규회원으로 다시 집계하지 않는다.

## 4. 공백 후보 생성 게이트

공백 후보를 만들기 전 다음 항목을 대조한다.

1. 기준 출석 시스템과 마지막 실제 참여 시각
2. 상품별 기대 수업 빈도와 계약상 이용 가능 기간
3. 미래 예약과 취소·재예약 계보
4. 승인된 휴회, 예정된 부재와 지점 이동
5. 휴강·공휴일·시설 문제·코치 부재 등 사업자 예외
6. 체크인 누락·동기화 지연·중복 회원 등 기술 예외
7. 기간제·횟수제·자유이용 등 상품 차이

공백 일수만으로 `INACTIVE_CONFIRMED`로 전환하지 않는다. 기준이 확정되지 않은 상품은 `GAP_REVIEW`로 유지한다.

## 5. 사유 기록 원칙

사유는 아래 증거 수준을 분리한다.

| 수준 | 예시 | 사용 범위 |
|---|---|---|
| 직접 확인 | 회원 또는 권한 있는 보호자가 말한 일정·결정 | 원문 최소화 후 승인된 코드로 기록 |
| 운영 확인 | 휴강, 휴회, 접근권 오류, 예약 충돌 | 운영 원천과 책임자 기록 |
| 분석 가설 | 시간대 불일치 가능성, 수업 난이도 우려 | 실험 가설로만 사용 |
| 미확인 | 아무 근거 없음 | `GAP_REASON_UNKNOWN` 유지 |

건강·부상·가족·직장 사정은 필요한 운영 인계 범위만 사용한다. 마케팅 담당자가 건강 상태를 판정하거나 공개 콘텐츠의 사례로 사용하지 않는다.

## 6. 연락 적격성 게이트

비활성 확정과 연락 가능성은 별도 판정한다.

- 연락 목적이 서비스 운영인지 광고성 복귀 권유인지 구분한다.
- 전송자, 브랜드, 지점과 채널별 동의 범위를 확인한다.
- 본사·지점 통합 수신거부와 철회를 대조한다.
- 미성년 회원은 보호자 권한과 수신 대상을 확인한다.
- 야간 전송, 빈도 상한과 중복 캠페인 억제를 적용한다.
- 자동 메시지와 사람의 실제 답변을 분리한다.
- 동의가 불명확하면 실제 발송하지 않는다.

정보통신망법 제50조는 영리목적 광고성 정보의 사전 동의, 수신거부·철회 반영, 야간 별도 동의와 전송자·수신거부 방법 표시를 규정한다. 출석 공백 자체는 이 요건을 대체하지 않는다.

## 7. 복귀 퍼널과 귀속

복귀 성과는 다음 사건을 순서대로 측정한다.

`공백 후보 → 검토 완료 → 연락 적격 → 실제 발송 → 전달 → 사람 응답 → 복귀 의사 → 복귀 예약 → 실제 참여 → 재활성 → 재등록 계약 → 실수납`

### 귀속 원칙

- 공백 후보 수를 발송 모수나 복귀 모수로 사용하지 않는다.
- 메시지 전달을 사람의 대화로 집계하지 않는다.
- 예약을 실제 복귀로 집계하지 않는다.
- 실제 복귀를 재등록 또는 수납으로 집계하지 않는다.
- 광고·네이버·당근·Instagram·직원 소개가 겹치면 하나의 회원 계보에 접점을 연결한다.
- 귀속기간이 승인되지 않았으면 채널별 복귀 기여를 확정하지 않는다.
- 자연 복귀와 연락 후 복귀를 분리한다.

## 8. 채널별 실행 원칙

### 네이버

- 공개 프로필의 시간표·휴무·예약 링크가 실제 지점 정보와 맞는지 확인한다.
- 예약 가능 여부와 회원의 이용권·출석 상태를 혼동하지 않는다.
- 리뷰 요청과 복귀 혜택을 교환하지 않는다.

### Instagram

- 코치 개인 계정은 수련·지도·유도 상식 중심으로 운영한다.
- 휴면·복귀 실적이나 회원 사유를 코치 개인 경험처럼 말하지 않는다.
- CTA는 게시물별 저장·댓글·질문·수업 문의 중 하나만 선택한다.
- 승인 대기 미디어와 캡션은 공개 저장소에 올리지 않는다.

### 당근·지역 채널

- 확인된 지점·수업·기간·가격만 안내한다.
- 실제 좌석 근거 없이 `마감 임박`, `이번이 마지막`을 쓰지 않는다.
- 문의·예약·방문·복귀·등록을 각각 측정한다.

### CRM

- 예정된 부재·휴회·사업자 예외를 먼저 제외한다.
- `오랜만이에요` 같은 표현도 실제 공백 정의와 연락 적격성을 통과한 경우에만 사용한다.
- 회원이 밝히지 않은 복귀 장벽을 단정하지 않는다.
- 미응답을 거절 또는 이탈로 바꾸지 않는다.

## 10. 최소 데이터 사전

공개 저장소에는 실제 회원 행을 넣지 않는다. 내부 시스템에서 필요한 최소 필드는 다음과 같다.

| 필드 | 정의 |
|---|---|
| `member_key` | 내부 가명 회원 식별자 |
| `branch_id` | 내부 지점 코드 |
| `membership_type` | 승인된 상품 유형 |
| `last_attended_at` | 기준 원천의 마지막 실제 참여 시각 |
| `future_booking_at` | 가장 가까운 미래 예약 시각 |
| `freeze_status` | 승인된 휴회 상태 |
| `planned_absence_until` | 확인된 예정 부재 종료 시각 |
| `business_exception_code` | 휴강·시설·기술 예외 코드 |
| `gap_rule_version` | 적용 공백 기준 버전 |
| `gap_review_status` | 후보·검토·확정·제외 상태 |
| `reason_evidence_level` | 직접 확인·운영 확인·가설·미확인 |
| `contact_eligibility` | 목적·전송자·채널 기준 연락 가능 여부 |
| `return_interest_at` | 복귀 의사 확인 시각 |
| `return_booking_at` | 복귀 예약 시각 |
| `return_attended_at` | 복귀 실제 참여 시각 |
| `reactivation_rule_version` | 적용 재활성 기준 버전 |
| `renewal_contract_at` | 재등록 계약 확인 시각 |
| `payment_verified_at` | 실제 수납 확인 시각 |
| `source_system` | 각 사건의 기준 원천 |
| `reviewed_by` | 판정 책임 역할 |

## 11. KPI 정의

모든 계산에는 분자·분모·기간·원천·기준 버전을 붙인다.

| KPI | 계산식 | 해석 제한 |
|---|---|---|
| 공백 검토 완료율 | 검토 완료 후보 ÷ 전체 공백 후보 | 비활성률이 아님 |
| 사업자 예외율 | 사업자 원인 공백 ÷ 검토 완료 후보 | 고객 이탈로 해석 금지 |
| 연락 적격률 | 연락 적격 후보 ÷ 비활성 확정 후보 | 실제 발송률이 아님 |
| 복귀 예약률 | 복귀 예약자 ÷ 적격 발송 도달자 | 실제 복귀율이 아님 |
| 실제 복귀율 | 복귀 실제 참여자 ÷ 적격 발송 도달자 | 자연 복귀 분리 필요 |
| 예약→복귀율 | 복귀 실제 참여자 ÷ 복귀 예약자 | 분모 0이면 계산 불가 |
| 재활성률 | 승인 기준 충족자 ÷ 복귀 실제 참여자 | 기준 버전 필수 |
| 재등록률 | 재등록 계약자 ÷ 재등록 결정 대상 | 실수납률이 아님 |
| 복귀 순수납 | 복귀 귀속 실수납 - 환불·승인된 비용 | 귀속기간·원천 필수 |

현재 파이널유도의 분자·분모·출석·수납 데이터는 연결되지 않았으므로 위 KPI 값은 모두 `데이터 미연결`이다.

## 12. EXP-342 — 공백 판정·복귀 귀속 완전성

### 목적

실제 고객에게 연락하지 않고 합성 회원 계보 30건으로 상태 판정과 귀속 오류를 검증한다.

### 필수 시나리오

- 미래 예약이 있는 출석 공백
- 승인된 휴회와 예정된 부재
- 휴강·시설 문제·체크인 누락
- 기간제·횟수제·복귀회원·지점 이동
- 복귀 의사만 있고 예약하지 않은 경우
- 예약했으나 사업자 취소된 경우
- 실제 복귀했으나 재등록하지 않은 경우
- 재등록 계약은 있으나 결제 미확인인 경우
- 수신거부·동의 불명확·미성년 보호자 권한 미확인

### 성공 기준

- 예정된 부재·휴회·사업자 예외의 비활성 오분류 0건
- 공백만으로 이탈 사유를 생성한 사례 0건
- 연락 부적격 대상의 발송 후보 포함 0건
- 복귀 예약의 실제 복귀 오분류 0건
- 복귀의 신규회원 중복 집계 0건
- 재등록 의사의 계약·실수납 오분류 0건
- 승인 없는 실제 메시지 발송·예약 변경·혜택 제공 0건

### 중단 기준

- 건강·부상·가족 사정을 임의 판정
- 수신거부자 또는 권한 미확인 보호자에게 연락
- 휴강·기술 오류를 고객 이탈로 처리
- 미확정 가격·시간·좌석·혜택 안내
- 개인식별정보를 공개 저장소나 실험 파일에 포함

복귀율·재등록률·순수납 목표는 `데이터 미연결`로 둔다.

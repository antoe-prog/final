# 최소 비식별 KPI 데이터 연결 규격 v1

- 문서 상태: 공개 가능한 데이터 규격
- 최초 작성일: 2026-09-14
- 최근 검토일: 2026-09-16
- 적용 범위: 신규 체험, 휴면 복귀, 기존회원 활성·만족·재등록, 검증 수납
- 기준 시간대: Asia/Seoul
- 공개 제외: 이름·연락처·생년월일·보호자 정보, 개인별 출석·건강·상담·계약·결제 원장, 비밀키·토큰, 승인 대기 콘텐츠, 미확정 행사·가격·혜택

## 1. 목적

파이널유도멀티짐의 마케팅 판단에서 반복되는 `데이터 미연결`을 해소하기 위한 최소 공통 입력 규격이다.

목적은 더 많은 개인정보를 모으는 것이 아니라 다음 사건을 같은 정의로 집계하는 것이다.

- 공개 콘텐츠와 채널 반응
- 유효 문의와 체험 예약
- 실제 체험 참석
- 검증된 신규 등록
- 신규회원 30일 활성
- 휴면 대상과 실제 복귀 출석
- 만료예정 계약과 검증 재등록
- 결제·환불·차지백 반영 순수납
- 수업 정원·예약·대기·실제 출석

플랫폼 조회를 문의로, 예약을 참석으로, 결제 시도를 매출로 바꾸지 않는다.

## 2. 공개와 비공개 경계

### 공개 저장소에 둘 수 있는 것

- 필드 이름과 정의
- 상태 코드
- 비율 계산식
- 익명 예시 행
- 검증 규칙
- 운영 체크리스트
- 공개 출처

### 공개 저장소에 두지 않는 것

- 회원·보호자 식별정보
- 연락처 또는 개인별 메시지
- 개인별 출석·건강·민원·계약·결제 기록
- 내부 회원 ID와 외부 플랫폼 계정의 연결표
- 지점별 미공개 실적·예산·손익
- 승인 대기 Instagram 이미지·캡션
- 미확정 FINAL ROAD 정보

실제 운영 데이터는 접근 통제된 비공개 기준 시스템에 둔다. 공개 보고에는 대표가 승인한 비식별 집계만 사용한다.

## 3. 공통 차원

모든 집계에는 적용 가능한 범위에서 다음 필드를 포함한다.

| 필드 | 정의 |
|---|---|
| `business_date` | Asia/Seoul 기준 영업일 |
| `event_at` | 사건 발생 시각 |
| `loaded_at` | 집계 시스템에 적재된 시각 |
| `observed_at` | 보고자가 원천 지표를 조회한 시각 |
| `source_timezone` | 원천 시스템이 날짜를 나누는 시간대, 미확인이면 `UNKNOWN` |
| `finalization_status` | `LIVE_SNAPSHOT`, `PROVISIONAL`, `RECONCILED`, `CLOSED`, `REOPENED` |
| `branch_code` | 승인된 비식별 지점 코드 |
| `program_code` | 승인된 수업·프로그램 코드 |
| `source_code` | 최초 유입원 코드 |
| `campaign_code` | 캠페인 코드, 없으면 `NONE` |
| `rule_version` | 적용한 정의·귀속 규칙 버전 |
| `source_system` | 기준 원천 시스템 |

| `extract_version` | 동일 기간 재추출 구분 |
| `correction_reason` | 늦은 반영·오류 수정 사유 |

지점 전체를 합산하기 전에 각 지점의 코드·기간·정의가 같은지 확인한다.

## 4. 0·공란·누락 규칙

- `0`: 기준 원천에서 해당 기간의 발생이 없음을 확인한 값
- `null`: 해당 필드가 적용되지 않거나 원천에서 제공하지 않는 값
- 행 누락: 적재 실패 또는 확인되지 않은 상태
- `-`: 화면 표시값일 뿐 숫자 0이 아님
- `DATA_MISSING`: 필요한 행 또는 필드가 없어 계산할 수 없음
- `DENOMINATOR_ZERO`: 분모가 확인된 0이므로 비율 계산 불가
- `WINDOW_IMMATURE`: 결과 관찰창이 끝나지 않음

누락값을 0으로 채우거나, 0%와 계산 불가를 같은 뜻으로 사용하지 않는다.

| `cta_type` | 저장·질문·팔로우·문의 중 하나 |

## 10. 코호트 전환 데이터셋

전환율은 같은 달의 서로 다른 총계를 나누지 않고 동일 코호트를 따라간다.

한 행의 단위는 `cohort_id × branch_code × source_code × rule_version`다.

| 필드 | 정의 |
|---|---|
| `cohort_id` | 비식별 코호트 키 |
| `cohort_start_date` | 코호트 진입일 |
| `maturity_date` | 결과 관찰창 종료일 |
| `inquiries` | 코호트의 검증 문의 |
| `bookings` | 같은 코호트의 확정 예약 |
| `attended` | 같은 코호트의 실제 체험 참석 |
| `contracts` | 같은 코호트의 검증 신규 계약 |
| `day30_active` | 성숙 코호트의 30일 활성 |
| `net_collected` | 직접 연결되고 대사된 순수납 |
| `attribution_status` | 직접 귀속·보조 접점·귀속 불가 |
| `window_status` | 성숙·미성숙·판정 보류 |

개인 식별 연결표가 필요하면 비공개 기준 시스템에만 두고 공개 집계에는 포함하지 않는다.

## 11. 최소 KPI 계산 규칙

모든 비율은 분자, 분모, 기간, 기준 원천, 규칙 버전을 함께 표시한다.

- 문의→예약률 = 동일 성숙 코호트의 확정 예약 / 검증 문의
- 예약→참석률 = 결과가 확정된 실제 참석 / 결과가 확정된 예약
- 참석→등록률 = 검증 신규 계약 / 결과창이 성숙한 체험 참석
- 등록→30일 활성률 = 활성 확정 / 30일 창이 성숙한 신규 등록
- 휴면 복귀 출석률 = 실제 복귀 출석 / 결과창이 성숙한 휴면 대상
- 재등록률 = 검증 갱신 계약 / 결과창이 성숙한 만료예정 계약
- 좌석 충원율 = 검증 참석 / 승인 정원
- 순수납 = 성공 수납 - 환불 - 차지백
- 순기여 = 순수납 - 승인된 직접비

분모가 0이면 계산하지 않는다. 원천이 없으면 `데이터 미연결`, 관찰창이 끝나지 않으면 `미성숙`으로 표시한다.

## 12. 기준 원천과 우선순위

대표 승인 후 시스템별 우선순위를 고정한다.

- 게시 성공: 공개 URL과 공개 계정 확인
- 플랫폼 반응: 해당 플랫폼 원본 또는 승인된 분석 도구
- 문의: 승인된 CRM·문의 원장
- 예약: 승인된 예약 시스템
- 참석: 승인된 출석 시스템
- 계약·휴회·해지·갱신: 승인된 회원권·계약 시스템
- 수납·환불·차지백: 승인된 결제·회계 원천
- 정원·휴강: 승인된 수업 운영 원천

원천이 충돌하면 임의 선택하지 않고 `REVIEW_REQUIRED`로 둔다.

## 13. 중복 제거와 수정

- 각 비공개 사건에는 불변 이벤트 키를 둔다.
- 동일 사건의 재수집은 건수를 늘리지 않는다.
- 지점 이동은 신규 등록으로 자동 계산하지 않는다.
- 상품 변경은 재등록 규칙을 충족할 때만 갱신으로 계산한다.
- 늦게 들어온 환불·차지백은 원래 수납 기간과 최신 보고 기간에 수정 이력을 남긴다.
- 과거 수치를 덮어쓸 때 `extract_version`, `loaded_at`, `correction_reason`을 기록한다.
- 이미 보고한 수치가 바뀌면 이전값·새값·변경 이유를 함께 남긴다.

### 13.1 시간대·데이터 신선도·마감 규칙

시간이 지나며 플랫폼 수치가 증가하거나 과거 값이 수정될 수 있으므로, 사건 발생 시각과 조회 시각을 분리한다.

#### 필수 원칙

- 원본의 `event_at`, 적재의 `loaded_at`, 조회의 `observed_at`을 각각 ISO 8601 오프셋과 함께 보관한다.
- 내부 영업일 `business_date`는 Asia/Seoul로 계산하되, 원천이 날짜를 나누는 시간대는 `source_timezone`에 별도로 기록한다.
- 원천 시간대를 확인하지 못한 날짜 코드를 임의로 한국시간으로 바꾸지 않고 `REVIEW_REQUIRED`로 둔다.
- 같은 수치가 반복 조회에서 유지됐다는 사실은 “해당 조회 시점에 새 값이 관찰되지 않음”을 뜻한다. 실제 활동 0건이나 플랫폼 마감을 뜻하지 않는다.
- 서로 다른 원천·지표 정의·조회 기간·시간대·마감 상태의 숫자를 같은 증감표에서 비교하지 않는다.
- 모든 스냅샷에는 `snapshot_id`, `observed_at`, `extract_version`, `source_timezone`, `finalization_status`를 둔다.
- 모든 채널에 24시간·72시간 같은 하나의 마감 규칙을 일괄 적용하지 않는다. 채널별 공식 처리 주기와 내부 운영 마감은 대표 승인 후 등록한다.

#### 마감 상태

| 상태 | 의미 | 의사결정 사용 |
|---|---|---|
| `LIVE_SNAPSHOT` | 진행 중인 기간의 조회값 | 모니터링만, 최종 성과 판정 금지 |
| `PROVISIONAL` | 기간은 끝났지만 원천 처리 또는 내부 대사가 끝나지 않음 | 방향성 참고, 예산·중단 판정 보류 |
| `RECONCILED` | 승인된 원천과 대조를 마침 | 성숙 조건 충족 시 실험 판정 가능 |
| `CLOSED` | 승인된 마감 시각과 검수 절차를 통과 | 공식 내부 보고 가능 |
| `REOPENED` | 마감 뒤 늦은 사건·환불·차지백·플랫폼 수정으로 재개 | 이전값·새값·사유를 함께 보고 |

#### 채널별 신선도 등록부

각 원천마다 다음 항목을 승인·관리한다.

| 항목 | 정의 |
|---|---|
| `metric_family` | 조회·도달·문의·예약·출석·계약·수납 등 |
| `source_document` | 공식 도움말 또는 내부 기준 문서 |
| `property_timezone` | 플랫폼 속성·프로필·광고계정의 기준 시간대 |
| `expected_refresh_interval` | 공식 또는 관찰로 확인한 갱신 주기 |
| `known_late_arrival_window` | 근거가 있는 경우의 늦은 반영 범위 |
| `operational_close_offset` | 내부에서 승인한 잠정→마감 대기시간 |
| `owner_role` | 원천 대사와 재개 승인 담당 역할 |
| `verified_at` | 정의와 도움말을 마지막으로 검증한 시각 |

#### 플랫폼별 적용 한계

- Google Analytics 4 공식 도움말은 데이터 처리에 24~48시간이 걸릴 수 있고 그동안 보고서가 바뀔 수 있다고 설명한다. 일부 데이터는 최대 7일 늦게 도착할 수 있고, 주요 이벤트의 기여도는 최대 12일 바뀔 수 있다. 이는 GA4에만 적용하며 Instagram·네이버·당근·회원관리 시스템의 마감 규칙으로 복사하지 않는다.
- Google 비즈니스 프로필 공식 도움말은 검색어 지표가 매월 초 갱신되며 표시까지 최대 5일 걸릴 수 있다고 설명한다. 조회는 사용자·기기·플랫폼과 일 단위 중복 제한을 반영하고, 길찾기 요청도 중복 탭·취소·스팸을 고려한다. 따라서 검색어·조회·길찾기·전화·예약을 같은 사건으로 합치지 않는다.
- Instagram·Metricool의 현재 지표는 실제 조회 시각과 원천을 기록하되, 이 문서에서 공식 처리 지연 상한을 확인했다고 간주하지 않는다. 승인된 마감 규칙이 없으면 `LIVE_SNAPSHOT` 또는 `PROVISIONAL`로 유지한다.
- 문의·체험·등록·복귀·재등록·순수납 원천이 연결되지 않았으면 플랫폼 지표가 마감돼도 하단 퍼널은 `데이터 미연결`이다.

#### 마감 후 수정 기록

마감값이 바뀌면 다음을 보존한다.

- `previous_value`
- `revised_value`
- `revision_observed_at`
- `revision_reason`
- `source_evidence`
- `approved_by_role`
- `reopened_period`

마감 후 수정은 이전 보고를 삭제하는 방식이 아니라 변경 이력을 추가하는 방식으로 처리한다.

## 14. 최소 품질 검사

### 구조

- [ ] 모든 행에 날짜·시간대·지점·원천·규칙 버전이 있음
- [ ] 사건·적재·조회 시각과 원천 시간대가 분리됨
- [ ] 모든 지표에 잠정·대사·마감 상태가 있음
- [ ] 마감 후 수정은 이전값·새값·사유·승인 역할이 남음
- [ ] 수업 단위와 일별 단위가 섞이지 않음
- [ ] 0·공란·행 누락이 구분됨
- [ ] 중복 이벤트 키가 없음
- [ ] 공개 산출물에 개인정보가 없음

### 퍼널

- [ ] 문의·예약·대기·참석·등록이 분리됨
- [ ] 같은 코호트와 성숙한 관찰창만 전환율에 사용됨
- [ ] 도장 취소를 노쇼로 계산하지 않음
- [ ] 지점 이동·테스트·중복이 신규 등록에서 제외됨
- [ ] 직접 귀속과 보조 접점이 분리됨

### 수납

- [ ] 성공 수납과 결제 시도가 분리됨
- [ ] 환불·차지백이 반영됨
- [ ] 비용의 승인·원천이 있음
- [ ] 순수납과 회계상 매출을 혼용하지 않음
- [ ] 동일 결제가 여러 채널에 중복 귀속되지 않음

## 16. 단계적 연결 순서

1. 지점 코드·프로그램 코드·원천 코드를 승인한다.
2. 문의·예약·출석·계약·결제의 기준 시스템을 하나씩 지정한다.
3. 최근 하루의 비식별 집계로 0·누락·중복 검사를 통과한다.
4. 7일 병행 검증으로 원장과 집계를 대사한다.
5. 성숙 코호트만 전환율 계산을 시작한다.
6. 지표 수정 이력과 담당자를 고정한다.
7. 이후에만 캠페인·CRM·수익 실험의 개선폭을 판정한다.

자동 고객 연락, 광고, 혜택, 계약 변경은 데이터 연결과 별개의 승인 대상이다.

## 17. EXP-306 — KPI 데이터 연결 완전성

- 목적: 네 사업 목표를 추정 없이 계산할 수 있는 최소 비식별 기준선 확보

- 성공 기준:
  - 날짜·지점·원천·시간대·규칙 버전 기록률 100%
  - 기준 원천 지정률 100%
  - 확인된 0과 누락 구분률 100%
  - 코호트 전환율의 분자·분모·성숙일·원천 기록률 100%
  - 중복 이벤트 0건
  - 교차지점 이중 계산 0건
  - 순수납의 결제·환불·차지백 대사율 100%
  - 사건·적재·조회 시각 및 원천 시간대 기록률 100%
  - 잠정값을 마감값으로 오분류한 건 0건
  - 마감 후 수정 이력 누락 0건
  - 공개 개인정보 0건

  - 지점 코드 또는 사건 정의 미확정

  - 관찰창과 성숙 조건 미승인
  - 원천 간 수치 충돌 미해결

  - 개인정보 또는 개인 원장을 공개 저장소에 업로드
  - 누락값을 0으로 변환
  - 서로 다른 코호트의 같은 달 총계를 나눠 전환율로 표현
  - 결제 시도·청구액을 순수납으로 표현
